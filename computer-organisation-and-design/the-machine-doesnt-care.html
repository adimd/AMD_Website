Computer Organisation & Design · Class 1

The Machine Doesn’t Care

Four things happened before I designed this course. A wallpaper destroyed phones. A number refused to add correctly on every device in the world. A clock has been ticking toward catastrophe since 1970. And a computer with 4 kilobytes of memory put a man on the moon. This class is about all four, and why they are the same story.

I want to be honest about why I teach this course the way I do. When I first started working with microcontrollers, I had no idea what was actually happening inside them. I could copy code, flash firmware, make LEDs blink. But I was just a passenger. The machine was doing things I could not explain, and I had no language for it. That frustration is the reason this class exists.

So we are not starting with a syllabus. We are starting with four stories. Each one is real, each one is recent enough that you might have lived through it, and each one traces back to the same handful of ideas this course will give you. By the end of today you will not have learned any of those ideas yet, but you will understand exactly why you need them.

Story 1 · The wallpaper that killed phones

In 2020, a photograph started circulating. A sunset over a lake, vivid, saturated, genuinely beautiful. The kind of image you would immediately want as a wallpaper. People set it on their Samsung Galaxy phones, their Google Pixels, their OnePlus devices. And then those phones never turned on again.

The video that inspired this story. Watch it first if you want the full experience, then come back here for what is actually happening inside the machine.

Not a virus. Not malware. A JPEG of a sunset.

The phone would show the boot screen, fail to start the interface, and try again. And again. The loop never ended. A factory reset was the only way out, and even that did not always work. Half a billion Android devices were vulnerable to a photograph.

This is the image. A lake. Mountains. A sky that goes from deep blue to warm orange at the horizon. It looks completely fine. You would set it as your wallpaper without a second thought.

St Mary Lake, Glacier National Park, Montana. Photo by Gaurav Agrawal, via BBC News. This is the actual image. Shot on a Nikon, exported from Lightroom in ProPhoto RGB. Perfectly valid photography. Permanently bricked phones on contact.

Now here is what actually happened, starting from one pixel.

Every pixel in an image is stored as three numbers: red, green, blue. On a standard display each of those three numbers lives in an 8-bit container, which means it can hold any whole number from 0 to 255. A red value of 0 is no red. A red value of 255 is the most red the screen can show. Everything between is a shade. The machine understands nothing outside that range.

This image was encoded in a format called Display P3, a wide-gamut color space used in professional photography. Wide-gamut formats can describe colors more vividly than a normal screen can display. But to actually show one of these images, the phone has to convert the P3 values into the smaller sRGB range the screen uses. That conversion is arithmetic, and for nearly every pixel it produces a value that fits fine within 0 to 255.

For one pixel in that sunset, it did not. The conversion arithmetic produced a luminance value that came out negative. Physically that makes no sense. A pixel cannot be darker than the absence of light. But the math does not know that. It just produced the result the formula gave it.

The machine did not know the number was wrong. It just used it.

Inside Android, there is a class called ImageProcessHelper. It scans every pixel of the wallpaper image, computes a value called y by summing the RGB components of the greyscaled pixel, and uses y as an index into an array. The array has 256 slots, numbered 0 to 255. When y came out negative for that one pixel, the code tried to access slot negative-something of the array. That slot does not exist. Java threw an ArrayIndexOutOfBoundsException. System UI crashed.

Android is designed to restart System UI automatically whenever it crashes. Normally this is a good thing. A brief crash, a quick restart, you never notice. But the first thing System UI does on restart is load the wallpaper. The wallpaper still has the same pixel. The same negative value. The same exception. System UI crashes again. Restarts again. Crashes again.

The crash loop that bricked the phone

The fix was one line. Before using y as an array index, clamp it: if it falls below 0, set it to 0. If it rises above 255, set it to 255. The array access is always valid. System UI never sees the bad value. The phone works fine.

One missing clamp. Half a billion devices. The engineer who wrote ImageProcessHelper was not careless. They simply never considered that a color space conversion could produce a value outside the range 0 to 255, because in the color spaces they had always worked with, it could not. The wide-gamut image was valid. The conversion was valid. The output was not in range. Nothing checked. Everything crashed.

That is the gap this course closes. Not carelessness. Just not knowing what the machine is actually doing with your numbers.

Why this is in the course
Everything inside a computer, colors, characters, sounds, instructions, is a number. Numbers are stored in containers of fixed size. When a number exceeds its container, the machine does not apologize. It crashes, wraps around silently, or gives the wrong answer. Understanding how numbers live inside fixed-width containers is the first thing this course teaches, in Module 1.

Story 2 · The number that lies on every device in the world

This one you can verify yourself later with a single line of C. But first, just think about it.

What is 0.1 plus 0.2?

Obviously 0.3. You learned this before you learned to read. Every calculator you have ever used agrees. Every spreadsheet. Your phone. Your laptop. The arithmetic is not in question.

Now write this in C and run it.

float_check.c#include <stdio.h> int main() { float a = 0.1, b = 0.2, c = 0.3; printf("a + b = %.17f\n", a + b); printf("c = %.17f\n", c); printf("equal? = %d\n", a + b == c); return 0; }
What the program actually prints

Not equal. Not even close to equal, once you look past the first 16 decimal places. The machine that runs your bank, your satellite navigation, your hospital equipment, all of them give this same answer. 0.1 + 0.2 is not 0.3. It never has been, on any computer that stores numbers in binary floating point.

This is not a bug anyone is going to fix. It is not a rounding mode setting you can change. It is a fundamental consequence of how numbers are stored inside a machine made of switches.

The machine is not wrong. You just do not know what it is actually storing.

Here is the problem. Your computer stores numbers in binary. In binary, the number 0.1 is a repeating pattern, 0.0001100110011... going on forever, in exactly the same way that one third in decimal is 0.3333... going on forever. The computer cannot store an infinite pattern. It cuts it off at a fixed number of bits and stores the nearest value it can. That stored value is not exactly 0.1. It is very close, but not exact. Same for 0.2. When you add two approximations, you get an approximation of the sum, and that approximation is not exactly 0.3.

Now here is where it gets stranger. Run this.

vanish.c#include <stdio.h> int main() { float x = 16777216.0f; // this is 2 to the power 24 printf("x = %.1f\n", x); printf("x + 1 = %.1f\n", x + 1); printf("equal? = %d\n", x + 1 == x); return 0; }
Adding 1 to a number and getting the same number back

You added 1 to a number and the number did not change. The 1 did not make the number slightly larger. It just vanished.

This happens because at the value 224, the gap between adjacent representable float values is exactly 2. There is no representable value between 16,777,216 and 16,777,218. So 16,777,216 + 1 = 16,777,217, which cannot be stored as a float, rounds back to 16,777,216. The 1 had nowhere to land.

The gaps between representable float values grow as numbers get larger

And now look at all three stories together. A color value that went slightly outside the range 0 to 255. A decimal that cannot be stored exactly in binary. A 1 that had nowhere to land. These are all the same sentence: a number that did not fit its container. Three different failures, one explanation.

Why this is in the course
Binary cannot represent most real numbers exactly. Every float you store is an approximation, and the gap between the real value and the stored value is not a bug. It is the machine working exactly as designed. This is precisely what this course is about. By the end of it, 0.1 + 0.2 == 0.3 returning false will feel completely obvious. You will know exactly what the machine stored and exactly why they do not match.

Story 3 · The clock that has been ticking since 1970

I came across this one while going down a rabbit hole of engineering decisions that seemed perfectly reasonable at the time and turned into catastrophes decades later. Once I saw it I could not stop thinking about it. It looks like a boring infrastructure problem. It is actually one of the most elegant examples of how a number, chosen carefully and deliberately by engineers who knew exactly what they were doing, becomes a timebomb the moment it outlives the people who made it.

I have seen this 1970 problem referenced so many times over the years. And every time, the framing is the same: engineers made a mistake. But they did not. What happened is more interesting than that.

On January 19, 2038, at exactly 03:14:07 UTC, a very large number of computer systems will simultaneously believe it is December 13, 1901.

Not because of a cyberattack. Not because of a software update gone wrong. Because of a decision made in 1970 by engineers who understood their machine completely, and whose decision has been quietly ticking ever since inside systems that most people have forgotten to think about.

Here is what they decided. Unix, the operating system that became the foundation of Linux, Android, macOS, and most of the internet, needed a way to represent time. The engineers chose to store time as a single number: the count of seconds elapsed since midnight on January 1, 1970. Simple, precise, easy to do arithmetic with. To store that count they chose a 32-bit signed integer.

A 32-bit signed integer can hold values from negative 2,147,483,648 to positive 2,147,483,647. That upper limit, in seconds from 1970, corresponds to January 19, 2038. One second after that, the counter overflows. It wraps from the largest positive value to the largest negative value. A negative timestamp, interpreted as a date, lands somewhere in 1901.

The Unix timestamp filling up

Now the important thing to understand is that the engineers who made this decision were not naive. Memory in 1970 was extraordinarily expensive. Choosing 32 bits over 64 bits for every timestamp in the system was a real and significant saving. They did the arithmetic. They knew the counter would overflow in 2038. They simply made a judgement that Unix would not still be running in 2038.

They were wrong about that.

Unix is now inside almost everything. Linux runs the servers that deliver this webpage. Android is built on a Linux kernel. Embedded systems inside power grid controllers, medical devices, industrial equipment, and traffic management systems were programmed once, deployed, and never updated. Many of them are still counting seconds in a 32-bit integer right now.

Some systems are already failing. Any software that needs to schedule something more than about twelve years in advance is already hitting 2038 dates. Mortgage systems. Long-term contracts. Infrastructure planning tools. The overflow is not waiting until 2038 for everyone.

The engineers who made this choice understood their machine completely. That is what makes this different from the wallpaper. The wallpaper was ignorance. This was knowledge, made by people who will not be around to deal with the consequences. And I genuinely think future generations will sit in front of systems that have quietly slipped to 1901 and have no idea why.

Computerphile on the 2038 problem. Worth watching before or after reading this. They explain the mechanics well.

Every engineer who has used time_t since 1970 has been trusting a 32-bit integer they have never looked inside. The people who created this problem are retired or gone. The systems they built are still running. And the engineers who will have to fix this are the ones who understand what a 32-bit signed integer actually is, what it can hold, and what happens when it runs out.

That is precisely what this course teaches.

Why this is in the course
Every data type has a size. Every size has a maximum. Every maximum has a moment when it runs out. This course teaches you to think about these limits as a matter of habit, not as an afterthought. The wallpaper engineer forgot to check. The 2038 engineers knew but the knowledge died with them. This course is about making sure that knowledge lives in you.

Story 4 · What 4 kilobytes can do

Everything so far has been about failure. A phone bricked by a photograph. A number quietly wrong on every machine on earth. A clock ticking toward 1901. This one goes the other direction entirely.

But to understand why it is extraordinary, you need to understand how many things went wrong first.

The Apollo program lost three astronauts in a fire on the launch pad in 1967, during a routine test. Gus Grissom, Ed White, Roger Chaffee. The hatch could not be opened from inside. The program was grounded for nearly two years. When it restarted, the pressure to make it work was immense in a way that is difficult to describe from the outside.

Apollo 10 flew to the moon and orbited it, but deliberately could not land. The lunar module was built slightly too heavy to make it back from the surface, removing any temptation to try. A full rehearsal with no possibility of the actual thing, even if everything worked perfectly.

Then Apollo 11. July 20, 1969. Neil Armstrong and Buzz Aldrin in the lunar module descending to the surface. Michael Collins alone in the command module orbiting above, with no way to help if anything went wrong below. The landing site turned out to be covered in boulders. Armstrong took manual control and flew past it, searching for somewhere flat, burning fuel he could not afford to burn. Thirty seconds of hover time remained when he finally touched down.

Somewhere in all of that, eight minutes before landing, something else went wrong.

The computer started throwing alarm codes. 1202. Over and over. Nobody on Earth had ever seen a 1202 in a real mission before. The flight controllers had seconds to decide whether to abort.

Now, before I tell you what that alarm meant: what do you think was inside that computer?

The Apollo Guidance Computer had 4 kilobytes of working memory. Your phone has 8 gigabytes. That is a two million fold difference. The AGC ran at 1 MHz. Your phone runs at 3 GHz across eight cores. The AGC had 12,300 transistors. The chip in your phone has 19 billion.

The Apollo Guidance Computer against what is in your pocket

The AGC was not miniaturised. It was roughly the size of a large hardcover book. What made it extraordinary was not what it had. It was how completely the people who built it understood every single part of it.

Every byte of those 4 kilobytes was accounted for. Every instruction was chosen deliberately. The software was literally woven into the computer by hand. Women at MIT threaded wires through magnetic rings, one bit at a time. A wire passing through a ring encoded a 1. A wire bypassing it encoded a 0. The entire flight program, navigation, guidance, control, was physically embedded in the hardware. If there was a bug after launch, there was no patch. No update. You had to get it right because you understood it completely.

So what was the 1202 alarm?

It meant the processor was overloaded. The rendezvous radar, which the crew had left on as a precaution in case they needed to abort and rejoin Collins above, was feeding the computer data it had not asked for. Too many tasks were competing for the same 4 kilobytes at once.

But the engineers who built the AGC's operating system had thought about exactly this. They had built a priority system for interrupts: a way of deciding which tasks were critical and which could be dropped when the processor was overloaded. Navigation mattered. Rendezvous radar data, when you are eight minutes from landing, did not. The system dropped what it could and kept flying.

Jack Garman, a 24-year-old engineer at mission control, had seen the 1202 code in simulations. He told his flight controller it was safe to continue. Flight director Gene Kranz made the call. Armstrong landed with 17 seconds of fuel remaining.

Pure computing brilliance. Not processing power. Not speed. Someone had thought, in advance, about what happens when everything tries to happen at once. And they built a machine that knew what to protect and what to let go.

Now look at the gap between that machine and yours. Two million times more memory. Twenty-four thousand times faster. One and a half million times more transistors. That gap is not magic. It is sixty years of engineering decisions, each one built on the understanding of the one before. Transistors to gates. Gates to circuits. Circuits to processors. Processors to the thing in your pocket.

Every layer of that stack runs on the same ideas: how you represent information in bits, how you move it through logic, how you execute instructions, how you manage memory, how you handle interrupts. The AGC had all of them. Your phone has all of them. The ideas did not change. Only the scale did.

The same concepts, from 1969 to today

The engineers who built the AGC understood what they had so completely that they could trust it with human lives at 384,000 kilometres from Earth with a 2.6 second communication delay. They had no choice. There was no debugging a crash on the lunar surface.

You have two million times more compute than they did. This course is about learning to understand what you actually have, the way they understood what they had. Not approximately. Not conceptually. The way you understand something when lives depend on it.

Why this is in the course
The AGC used binary representation, a stored program, an instruction set, and an interrupt system. Those are not historical curiosities. They are the exact same ideas inside every computer built today, and they are exactly what this course teaches. The only difference between 1969 and now is scale. The concepts have not changed at all.

What these four stories have in common

A wallpaper that destroyed phones. A float that gives the wrong answer on every machine on earth. A timestamp that has been running out since 1970. A 4KB computer that landed on the moon.

Three of those are failures. One is the opposite of failure. But they all trace back to the same thing. Whether the engineer understood what the machine was actually doing with their numbers.

The wallpaper engineer did not think about what happens when a color value exceeds the container holding it. The float is wrong because nobody told you that 0.1 is not 0.1 inside a computer. The 2038 problem exists because engineers used a timestamp without asking what was inside it. And Apollo worked because the engineers knew every clock cycle, every byte, every interrupt, of a machine with less memory than a text message.

The machine has been inside everything that shaped your world. The mission that put people on the moon. The app you used to pay for something this morning. The timebomb ticking inside systems older than your parents. The wallpaper that turned an expensive phone into a paperweight.

It does not care whether you understand it. It runs for engineers who do and fails for engineers who do not, with complete indifference.

This course is about understanding what is inside the box. Everything else follows from that.
