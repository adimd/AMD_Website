Data Has a Shape: How PCA Discovers It

Data Has a Shape

An honest question to start a series with: how many real numbers does it take to store this dataset? The naive answer is the obvious one. It's also wrong by a lot.

A small problem with a small dataset

Question. How many real numbers do you need to write this dataset down on a disk?

The first answer everyone gives is eight. Four points, two coordinates each, eight numbers. That's also the answer a computer would give if you asked it nicely. Store the table, you're done.

Now look at the points for a second longer.

−14 is twice −7. 4 is twice 2. 1 is twice 0.5. 0 is twice 0.

Every single point sits exactly on the line \(y = 2x\). Not approximately. Not roughly. Exactly. So somewhere in those eight numbers we're being repetitive. We wrote down the y-coordinate for every point even though, for this dataset, the y-coordinate is just the x-coordinate scaled by two. We could have written down only the x-coordinate of each point and reconstructed the y from a single rule.

That's four numbers for the x-coordinates, plus a couple more to remember the rule itself. Six numbers, not eight. We just compressed the dataset by a quarter, and we did it without losing a single thing.

Direction, then position along it

Let's pin down what just happened, because it's the entire idea this series is built on.

Instead of storing each point as a pair of coordinates, we made two observations. First, all the points share a direction. They all lie along the same line, which has slope 2, which we can encode as the unit vector pointing along \(y = 2x\). Second, each point has a position along that line. Some are far out, some are close to the origin, some are negative. That position is a single number per point.

So the recipe becomes:

  • Once, store a direction. For 2D data, that's two numbers.
  • Per point, store one number telling us where on that direction the point lives.

For our four points, that's \(2 + 4 = 6\) numbers. The naive way needed \(2 \times 4 = 8\). Same data, fewer numbers. We didn't approximate anything. The savings came from noticing that the data wasn't really using both dimensions it was given.

Why this matters when n gets big

Saving two numbers on a four-point dataset is not going to win awards. The interesting thing isn't the absolute saving, it's how the saving grows.

If you have \(n\) data points each living in \(d\) dimensions, the naive storage cost is \(n \times d\). One number per coordinate per point. But if all the points lie on a single line in that \(d\)-dimensional space, the smart storage is \(d + n\): the direction vector once, plus one position per point.

For four points in 2D the saving is barely worth the effort. Push the slider. With a thousand points the naive method needs two thousand numbers. The smart method needs one thousand and two. The savings get more dramatic the more points and dimensions you have, because \(n \times d\) grows fast and \(d + n\) doesn't.

This is the whole motivation for what's coming. Real datasets are big. The number of points and the number of dimensions are both large, often very large. If we can write our data as a direction (or a few directions) plus a small set of positions per point, the savings stop being a curiosity and start being the difference between a dataset that fits in memory and one that doesn't.

The honest catch

You've already spotted the problem. Our four points sat exactly on the line \(y = 2x\). Real data does not do this.

If I gave you the heights and weights of a hundred people, the points would lean towards a line, but they wouldn't sit on one. Tall people are usually heavier, but not in lockstep. There's noise. There's variation. There's the friend of yours who's six foot four and weighs ninety kilograms next to the friend who's five foot ten and weighs ninety-five.

So the question isn't whether real data lies on a line. It doesn't. The question is whether real data lies close to a line, and if so, whether we can use that closeness to compress at the cost of a small, controlled amount of error.

Exact compression works only when the data was already structured. Useful compression has to be willing to lose a little.

That single shift, from "exact" to "close enough", is what turns the storage trick from a curiosity into Principal Component Analysis. It's also the entire content of the next post.

What we have so far

One idea. Storage cost is the lens. The naive way to store \(n\) data points in \(d\) dimensions is \(nd\) numbers. If those points happen to share a single direction, we can rewrite the dataset using \(d + n\) numbers without losing anything. The savings are dramatic when \(n\) and \(d\) get large.

One catch. This worked because the data was perfectly structured. Real data isn't. What we want is a version of this trick that works on data with noise, that gives us a controlled approximation rather than an exact rewrite.

One thing to carry forward. The idea that data might use less space than it occupies. That a dataset's natural description might be smaller than its naive description. We're going to spend the rest of the series turning that suspicion into an algorithm.

Where this is going

Next time we take the same setup but break the assumption that points lie exactly on a line. We'll set up the question of how to approximate data with a direction, define what error means, and watch the algebra of "how close can we get" start to write itself. By the end of Part 2 we'll have a sharp problem to solve. After that, we solve it.
