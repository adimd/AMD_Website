Digital Logic for the Embedded ML Engineer

Fixed-Point Arithmetic

If float32 is the cleverest hack in computing, fixed-point is the most ruthless. It throws away everything float32 added and gets fractional arithmetic for almost free. Here's the deal.

What we just gave up

Last post we walked through the IEEE 754 float32 format in detail. We saw the genuine cleverness: a sign bit, a biased exponent, and an implicit-leading-1 mantissa, packed into 32 bits and trading uniform precision for an enormous dynamic range. Float32 is what your laptop uses for everything. It is also, structurally, why floating-point hardware is large and expensive.

This post is about the format that powers DSP and embedded ML. It will look almost embarrassingly simple after float32. That simplicity is the whole point. We're going to design a format that solves every one of float32's failures by giving up everything float32 added.

Float32 had four properties we didn't like for embedded ML:

  • Hardware was expensive because the binary point's position varied between values, so every operation had to align them at runtime.
  • It wasted bits on a dynamic range we'd never use (10⁻³⁸ to 10³⁸ when our weights live in ±1).
  • Precision was non-uniform, dense near zero and sparse far away, making error analysis hard.
  • Even simple decimals couldn't be stored exactly, with errors that depended on magnitude.

Let's design our way out of each of these in turn.

Design move 1: fix the binary point's location

The deepest reason float32 hardware is expensive: the binary point can be in different places for different values. A float holding 5.5 has its point at one position. A float holding 0.0001 has it at another. Every arithmetic operation has to figure out where the point is for each operand and align them before doing math. That's where most of the FPU's silicon goes.

Our first design choice is the obvious response: lock the binary point in place. Promise that it will sit at the same position for every value of a given type. The hardware never has to align anything because the alignment is permanent.

This is the source of the name. The binary point doesn't float. It's fixed. Locked by convention.

When the point is fixed, we don't need to store its position in the bits. The position is implicit. It lives in the type system, in our variable names, in our code's assumptions. The hardware just sees integers.

An integer in a register, plus an agreed-upon scale factor that lives only in your code. That's the whole idea.

Design move 2: use every bit for the value itself

Float32 spends 8 of its 32 bits encoding the exponent. Those bits buy enormous range. For neural network weights, we don't need that range. Trained weights live in roughly ±2. Activations after a ReLU rarely exceed a few hundred. So we can drop the exponent field entirely. Use every bit for the value itself.

An 8-bit fixed-point register gets 8 bits of integer value (with the binary point implicit somewhere). A 16-bit one gets 16. Each bit pulls its full weight in representing magnitude.

What we give up: dynamic range. To represent something outside our chosen range, we have to change the format or rescale. Float32 handled this automatically through its exponent. We don't get that for free anymore. We pay for it with engineering judgement.

Design move 3: make precision uniform

Float32's patterns are concentrated near zero and sparse far away. Two consecutive float32 values near 1.0 differ by about 10⁻⁷, but two near 10⁹ differ by about 64. This makes float arithmetic surprisingly hard to reason about.

If we drop the exponent and use all bits as a plain integer, every representable value is the same fixed step from its neighbours. Always. The gap between consecutive values doesn't depend on magnitude. For DSP and control systems, where you need to analyse error bounds, this predictability is essential.

What we give up: the gracious automatic adaptation float32 offered. We have to choose the step size deliberately at design time.

Design move 4: errors are bounded and known

We can't fix the deep fact that most decimals (0.1, 0.2, 0.3) have repeating binary expansions. That's a property of base 2, not of any specific format. But we can mitigate the consequences.

In float32, rounding behaviour is complex because the mantissa is a normalised fraction with an exponent. The error per number depends on magnitude. In fixed-point, with all bits as a plain integer at a uniform scale, the error is at most half the step size. Always. No exceptions, no surprises.

If we use 8 bits with a step of 0.0156 (which we'll see in a moment), every value rounds to the nearest multiple of 0.0156. Maximum error per number is 0.0078. We know this in advance.

The format we just designed

Putting all four moves together:

  • Binary point is fixed, position implicit by convention.
  • No exponent field; all bits go to the value.
  • Spacing between representable values is uniform.
  • Errors are bounded and predictable.

This is fixed-point. The whole arithmetic of fixed-point follows from these four choices.

Notice the trade we made: we threw away dynamic range and automatic adaptation, in exchange for cheap hardware (just an integer ALU), uniform precision, and predictable error. For embedded ML and DSP, where the data lives in known bounded ranges, this is exactly the right trade.

Where Q-format came from

Fixed-point arithmetic predates digital electronics. Mechanical calculators used it. So did the first electronic computers in the 1940s. The reason was prosaic: float hardware didn't yet exist.

What turned ad-hoc fixed-point into the structured Q-format notation we use today was the rise of dedicated digital signal processors in the late 1970s. Texas Instruments released the TMS32010 in 1983, the first widely-deployed single-chip DSP, and it had no FPU. To do useful audio processing on this thing, programmers had to think carefully about scaling. The Q-format notation emerged as the way to document and reason about those choices: a number in Q1.15 is a 16-bit value with one sign bit and 15 fractional bits, range −1 to nearly +1, resolution 1/32768.

By the early 1990s, Q-format was the lingua franca of audio DSP. Filters, FFTs, codecs, all of it was specified in Q-format conventions. ARM eventually codified this into the CMSIS-DSP library, which exposes q7_t, q15_t, and q31_t types. They're really just int8_t, int16_t, and int32_t underneath, but the typedefs document the implicit scale, which is exactly the discipline DSP engineers have practiced for forty years.

Encoding values: the scale factor in numbers

Let me make this concrete. Take an 8-bit format with the binary point in the middle: 4 integer bits, 4 fractional bits. The bit weights are:

position: 7 6 5 4 . 3 2 1 0 weight: 8 4 2 1 . ½ ¼ ⅛ 1/16

The smallest weight is 1/16. To express all the weights as multiples of 1/16, multiply everything by 16:

position: 7 6 5 4 . 3 2 1 0 weight: 128 64 32 16 . 8 4 2 1 (in units of 1/16)

That right column is just the byte read as a plain integer. So a byte that represents the real value 3.25 in this format also reads as the integer 52. They're the same byte, two interpretations:

  • As a fixed-point value: 3.25
  • As a plain integer: 52
  • And: 52 / 16 = 3.25 ✓

That factor of 16 is the format's scale factor. More generally, a format with n fractional bits has scale factor 2ⁿ. This is the relationship that connects "the integer the chip stores" to "the real number you mean":

integer in register = real value × 2ⁿ.
To read back: real value = integer / 2ⁿ.

That's why fixed-point scale factors are always powers of 2. The binary point can only sit between bit positions, and each bit weight is exactly twice the next, so the implicit divisor is always 2ⁿ. There's no fixed-point format with scale 100 or 7 or 1000. Binary forces the choice.

This will turn out to matter when we get to quantisation in the next post. Quantisation generalises the fixed-point trick by allowing arbitrary scale factors, which lets us match the data's actual range more efficiently at the cost of slightly more expensive conversion.

Q-format notation

The standard way to write a fixed-point format is Qm.n, where m is the number of integer bits and n is the number of fractional bits. Total bit width is m + n. For signed formats, one of the integer bits is the sign bit, leaving m − 1 bits for magnitude.

Some common formats:

  • Q1.7: 8 bits, 1 sign + 7 fractional. Range about ±1, resolution 1/128 ≈ 0.008. The dominant format in quantised neural networks.
  • Q1.15: 16 bits, 1 sign + 15 fractional. Range about ±1, resolution 1/32768 ≈ 3 × 10⁻⁵. The dominant format in audio DSP.
  • Q1.31: 32 bits, 1 sign + 31 fractional. Range about ±1 with very fine resolution. Used as the intermediate format for high-precision DSP work.
  • Q4.4: 8 bits, 4 integer + 4 fractional. Range about ±8, resolution 1/16. Useful when values exceed ±1.

The signed integer bits behave exactly like an m-bit two's complement integer. Same range. Same sign-bit-as-MSB. Same asymmetry where the negative side reaches the boundary exactly but the positive side stops one resolution short. Everything we know about two's complement carries over to fixed-point unchanged. Fixed-point is just two's complement integers with a different interpretation of the bit weights.

Adding fixed-point numbers: nothing to it

If two operands share the same fixed-point format, addition is just integer addition. Both operands have the binary point in identical positions, so when we add them column-by-column the result naturally has the binary point in the same place.

To add 2.5 + 1.25 in Q4.4: encode each as integers (2.5 × 16 = 40, 1.25 × 16 = 20), add the integers (40 + 20 = 60), decode (60 / 16 = 3.75). Done. The chip's int8 adder produced the right answer in one cycle. No alignment hardware. No normalisation. No exponent bookkeeping.

Compare to float, where every addition involves a sequence of steps: compare exponents, shift the smaller mantissa to align, add the mantissas, possibly normalise, round. Fixed-point pays the alignment cost once at design time when we choose the format. After that, every addition is free.

This is also why a quantised neural network layer can sum thousands of products into a 32-bit accumulator without any rescaling between them. All the products share the same combined scale (weight scale times activation scale), so they're all in the same fixed-point format. Addition just works. The only rescale happens once at the end of the layer, when we convert the accumulator back to int8 for the next layer's input. We saw this in the overflow lesson; now you can see why it works structurally.

One wrinkle. If two operands are in different formats, you have to convert one to match the other before adding. Conversion is a bit shift (because all scales are powers of 2), so it's cheap, but it's a real cost you have to remember. In well-designed DSP code, formats are chosen so cross-format conversions are rare.

Multiplying fixed-point numbers: the rescale

This is where fixed-point gets interesting. Watch what happens when we multiply 2.0 × 3.0 in Q4.4.

Encode: 2.0 → 32, 3.0 → 48. Multiply the integers: 32 × 48 = 1536. Now ask: what does 1536 represent?

Trace through symbolically. The first operand was 2.0 × 16, the second was 3.0 × 16:

result_integer = (2.0 × 16) × (3.0 × 16) = 2.0 × 3.0 × 16 × 16 = 6.0 × 256 = 1536

The integer 1536 represents the real value 6.0, but at scale 256, not at scale 16. The two scale factors of 16 multiplied together gave 256. Multiplication squared the scale.

This is the fundamental rule: multiplying two Q.n numbers gives a result in Q.2n. The number of fractional bits doubles, because in real-value terms the scale factor squared (and squaring in the exponent is doubling the fractional bits). It's the same as grade-school decimal multiplication: when you multiply numbers with N decimal places each, the result has 2N decimal places. Same idea, base 2 instead of base 10.

If we want to feed this result into the next stage that expects Q4.4, we have to rescale. Convert from scale 256 back to scale 16: divide by 16, which is a right shift by 4.

1536 >> 4 = 96 → 96 / 16 = 6.0 ✓

That right shift is the signature operation of fixed-point arithmetic. Every multiplication needs one downstream. The shift count equals the number of fractional bits in the operands. Q.7 multiplications need >> 7. Q.15 multiplications need >> 15. Q.31 multiplications need >> 31. Whenever you read DSP code and see (a * b) >> 15, that's a Q1.15 multiplication being rescaled.

The rescale is cheap in cycles but lossy in precision. Shifting right by N throws away the bottom N bits of the wider product. Those bits represented fine-grained contributions to the answer that we can't recover. For a single multiplication the loss is small. For chained multiplications, the precision losses pile up.

The trick that real DSP code uses: keep the wider intermediate as long as possible. Multiply more Q.n operands into the wider format, accumulate, and rescale just once at the end. This is exactly the int32 accumulator pattern from the overflow lesson, now with a richer justification. The wide accumulator isn't only for avoiding overflow. It's also for avoiding precision loss from premature rescaling. The two reasons reinforce each other.

Try −1 × −1. The mathematical answer is +1. The wider Q2.14 intermediate computes it correctly, but Q1.7 can't represent +1 (its max is +0.992). The naive shift wraps the result to −1. This is the saturating-multiply hazard. Real DSP libraries use a saturating version of multiply specifically to clamp this case to +0.992 instead of letting it flip sign.

The range vs precision tradeoff

When you pick a Q-format, you're really making two decisions at once. The integer bits determine the range. The fractional bits determine the resolution. For a fixed total bit width, you can have one or the other but not both. Every integer bit you take is a fractional bit you give up.

Three different 8-bit formats illustrate the spectrum:

  • Q8.0: range −128 to +127, resolution 1. Plain int8. No fractional capability at all.
  • Q4.4: range about ±8, resolution 1/16 ≈ 0.0625. Useful for moderate-magnitude values that need some fractional precision.
  • Q1.7: range about ±1, resolution 1/128 ≈ 0.008. The format used in quantised neural networks, where weights live in a tight range around zero.

All three formats use the same 8 bits. They have the same number of distinct representable values (256). They cover wildly different ranges with wildly different resolutions. This is the fixed-point engineer's main lever: same hardware, different format choices, optimised to the data.

Where this leaves us

Six things to take with you.

Fixed-point is "an integer with an implicit scale factor." The integer lives in hardware. The scale lives in your code. You agree on the scale at design time and apply it whenever you need real-valued results.

The scale factor is always 2ⁿ, where n is the number of fractional bits. This is forced by the binary structure of the format. Conversion between formats is a bit shift, so it's cheap.

Adding two same-format fixed-point numbers is just integer addition. The hardware doesn't even know there's a "binary point." All the alignment cost was paid at design time.

Multiplying two Q.n numbers produces a Q.2n result. The fractional bits double, equivalently the scale factor squares. To return to Q.n, shift right by n. Every multiplication in fixed-point code carries this rescale somewhere downstream.

The Q-format choice is a tradeoff between range and resolution. Q1.15 dominates audio DSP because audio samples live in ±1. Q1.7 dominates quantised NN inference because weights live in ±1 after scaling. Q4.4 and Q8.8 show up in control and graphics where values exceed ±1.

Fixed-point inherits two's complement entirely. The signed integer bits work exactly like a two's complement integer. The same overflow rules, the same flag behaviour, the same boundary asymmetry, the same −1 × −1 wraparound hazard. Fixed-point is just two's complement integers with a different interpretation of the bit weights.

Next post we relax one rule. Instead of forcing the scale to be a power of 2, we'll allow any scale we want, plus an integer offset called a zero-point. That extra freedom is the difference between fixed-point and quantisation, and it's what makes TFLite Micro and CMSIS-NN tick. We'll see what one quantised layer actually computes, end to end.
