Digital Logic for the Embedded ML Engineer

Bits in Memory

Why memory dumps look backwards, why one register holds sixteen settings, and the small set of patterns that make every datasheet readable.

Why this lesson exists

By now you can read a single byte. 0x9C doesn't scare you. You see 1001 1100 and you know which bits are set and which nibble is which.

The problem is that real hardware almost never deals with one byte at a time. It deals with values that span multiple bytes. A 32-bit weight. A 16-bit ADC reading. A 64-bit timestamp. And it packs many small fields into one register. A single 32-bit GPIO config register on an STM32 holds the mode for sixteen different pins, two bits per pin.

So now we have two new questions. When a value is bigger than one byte, in what order are those bytes laid out in memory? And when one register holds many small fields, how do we know which bits belong to which field, and how do we read or write them without disturbing the others?

Both questions have clean answers once you see them, but both have a couple of traps that will absolutely bite you if you don't know they exist. By the end of this post you'll be able to look at a memory dump and a datasheet at the same time, and tell me what the chip is doing.

Memory is just a long row of byte-shaped slots

Memory in a chip is an array of bytes, each with its own address. On a Cortex-M, addresses are 32-bit numbers, and each address points to exactly one byte. Address 0x20000000 holds one byte. Address 0x20000001 holds the next one. And so on, all the way up.

This part is fine. The complication is what happens when you want to store something bigger than one byte.

Suppose you want to store the 32-bit value 0x12345678 at address 0x20000000. That value is four bytes: 0x12, 0x34, 0x56, 0x78. Memory has slots at 0x20000000, 0x20000001, 0x20000002, 0x20000003. Four slots, four bytes. The question is which byte goes in which slot, and there are two reasonable answers. History picked both. That's the entire reason we have to talk about endianness.

The two answers

The question is whether the most significant byte goes at the lowest address, or the least significant byte does.

Big-endian puts the most significant byte first. So 0x12345678 stored starting at 0x20000000 looks like 12 34 56 78 in memory order. This matches how you read it left to right on paper. The "biggest" part of the number comes first. It's the natural-looking choice.

Little-endian puts the least significant byte first. Same value, same starting address, looks like 78 56 34 12 in memory. The "smallest" part comes first. This looks backwards if you're reading bytes left to right, but it has some quietly clever properties at the hardware level.

A small detour: where the name actually comes from

The names sound like they were invented by someone trying to be deliberately confusing, but there's a reason behind them, and it's surprisingly funny.

The terms come from Jonathan Swift's Gulliver's Travels, written in 1726. In the book, the tiny kingdom of Lilliput is in the middle of a long, bitter civil war. The two sides are the Big-Endians and the Little-Endians. They are not arguing about politics, religion, or land. They are arguing about which end of a boiled egg you should crack open first.

The Big-Endians say you crack the egg at the big end, the way nature intended. The Little-Endians, following an edict from a previous emperor (whose father had once cut his finger cracking the big end), insist you must crack the small end. This disagreement has, by the time Gulliver shows up, caused multiple wars, the deaths of "many thousands", and the loss of an entire fleet of warships. Swift was satirising the religious wars of his time. The point was that people fight bitterly over distinctions that don't really matter.

In 1980, a computer scientist named Danny Cohen wrote a famous paper called "On Holy Wars and a Plea for Peace", comparing the byte-order debate in computing to exactly this. He proposed the names "big-endian" and "little-endian" as a half-joke, because the engineering community was getting religious about it. The names stuck. Forty-five years later we're still using them, mostly because nobody has come up with anything better.

So when you say a chip is little-endian, you are quite literally calling it an egg-cracker from the small-end faction of an imaginary civil war. The history of computing is full of jokes that became permanent.

Little-endian: low byte at low address. Big-endian: high byte at low address. That's the whole distinction.

Why both exist

The big-endian argument is short. It matches how humans write numbers. When you write 1234 you write the thousands first, then hundreds, tens, ones. Most significant first. Big-endian is just the on-paper convention applied to bytes.

The little-endian argument is more interesting. Imagine you've stored a 32-bit value at some address, and now you want to read just the low byte of it as an 8-bit value. With little-endian, the low byte is already at the starting address. Read one byte from that address and you're done. With big-endian, the low byte is three slots further along, so you have to do address arithmetic. The same is true if you ever want to "shrink" a value from 32-bit to 16-bit. Little-endian makes those casts essentially free.

Little-endian also makes incrementing a multi-byte counter slightly cleaner in hardware, because the carry propagates "forward" through memory, in the natural direction of an iterator. Neither argument is decisive on its own. The world has just settled on different defaults in different places.

Who uses what

Practically speaking, for embedded ML, almost everything you'll touch is little-endian.

  • ARM Cortex-M (M0, M3, M4, M7, M33). Little-endian by default. Technically configurable, but you'll never see it any other way in the wild.
  • ARM Cortex-A, the application processors in phones and Raspberry Pis. Little-endian.
  • ESP32, both the Xtensa and the newer RISC-V variants. Little-endian.
  • x86 and x86-64, the laptop you're reading this on. Little-endian.
  • RISC-V. Little-endian by default.
  • Most modern GPUs and ML accelerators. Little-endian.

Big-endian survives in a few places. Network protocols are explicitly big-endian (the term for that is "network byte order"). Some legacy MIPS and PowerPC systems. A few file formats here and there.

So you'll be living in a little-endian world. But you should recognise big-endian when you see it, because it shows up the moment you start parsing network packets or certain file formats, and you don't want to be confused.

The bug this causes, and how to spot it

The classic embedded ML version of this bug is moving a model between systems. Train on a laptop. Save weights as raw bytes to a binary file. Load on the target chip. If both ends are little-endian, no problem. If one is big-endian, every multi-byte weight gets silently scrambled. The bytes arrive correctly. Their order is wrong. Inference produces nonsense and there's no error message anywhere.

You'd just byte-swap on load and the problem disappears, but only if you knew to look for it.

The other place endianness shows up is when you read memory dumps. A dump shows you bytes in address order. The value they encode is in some other order, depending on endianness. So when you see this on a little-endian chip:

0x20000000:  78 56 34 12

Your gut wants to read this as 0x78563412. But on a little-endian machine, those four bytes encode the value 0x12345678. The bytes appear in address order; the value is byte-swapped relative to that. You'll do this mental reversal a hundred times in your career.

Little-endian dumps look backwards. The bytes you see are in address order; the value is byte-swapped from what you read.

The thing that makes int8 quietly wonderful

There's a small but practically important consequence of all this. Endianness only matters for values that span more than one byte. The moment your storage unit is exactly one byte, there is no ordering question to get wrong.

This has a delightful side-effect for embedded ML. An int8 quantised model is endianness-immune. Each weight is one byte. There's no "low byte" and "high byte". If you write the bytes correctly on one machine, they read correctly on any other machine, regardless of endianness. You can ship a quantised .tflite file across architectures without ever thinking about byte order.

If you stored those same weights as float32, you'd have four bytes per weight, and you'd have to be careful. Int8 quantisation makes the problem disappear. This isn't the main reason int8 wins on embedded targets, but it's a real engineering virtue worth knowing about.

The other half: many fields in one register

Endianness is about how multi-byte values are laid out in memory. Register layouts are about how multiple settings are packed into one register. Both are about "how do bits get arranged?", just at different scales. Endianness operates at the byte level. Register layouts operate at the bit level.

This second one is where reading datasheets becomes a real skill, and it's the skill you'll use literally every time you configure a peripheral or talk to an accelerator.

What a register actually is

On a Cortex-M, a register is a fixed-size memory location at a known address. They're typically 32 bits wide. Each peripheral on the chip — a GPIO controller, a UART, a timer, an ADC, a DMA channel, an accelerator — has a small set of registers that you read and write to control it.

The trick is that a register isn't usually used as one big 32-bit number. Its bits are divided into fields, each controlling a specific aspect of the peripheral.

Here's a real example, lightly cleaned up. The STM32F4's GPIOA_MODER register controls the mode of the 16 pins on GPIO port A. Each pin gets two bits to specify its mode: input, output, alternate function, or analog. Sixteen pins times two bits is exactly thirty-two bits. The whole register is sliced into sixteen tiny 2-bit fields, one per pin.

This is how almost every hardware peripheral is configured. One register, many fields, each one a tiny knob you can turn. Reading and writing those knobs without disturbing the others is the core skill.

How datasheets describe the layout

You'll see register layouts in three common forms. They all mean the same thing.

The first form is a bit table. It looks like this.

| Bits | Name | Description | | 31:16 | RES | Reserved (write 0) | | 15:8 | DIV | 8-bit clock divider | | 7:5 | MODE | Operating mode (3 bits) | | 4 | IE | Interrupt enable | | 3:0 | CH | Channel select (4 bits) |

The notation [high:low] means "a range of bits from high down to low, inclusive." So 15:8 means bits 15, 14, 13, 12, 11, 10, 9, 8. Eight bits in total. The low bit and the high bit are both part of the field.

The second form is a visual diagram, where each field is a box and the box widths are proportional to the number of bits. Same information, just drawn instead of tabulated.

The third form is a list of offsets, "MODE: bits 4-6, 3 bits wide", and so on. Same information again. You'll see all three. They're equivalent.

Reading and writing fields in C

The two operations you do on a register all the time are extracting a field and inserting one. Both are mechanical, and both are built from a tiny vocabulary of bitwise operators.

Extracting a field

Shift the field down to the bottom, then mask to keep only its bits. To grab the 4-bit CH field at bits 0-3:

uint32_t ch = ctrl & 0xF; // already at the bottom, just mask

The mask 0xF is 0000 1111, which keeps the bottom four bits and clears everything else. No shift needed because CH is already at position 0.

To grab the 3-bit MODE field at bits 5-7:

uint32_t mode = (ctrl >> 5) & 0x7; // shift down, then mask

Shift right by 5 to move the field's lowest bit to position 0. Then mask with 0x7 (which is 0000 0111) to keep only those three bits.

The general pattern is (reg >> field_low_bit) & ((1 << field_width) - 1). Once your eye sees that shape it's a free read.

Inserting a field — and the trap

This is where most learners write a bug the first time, and it's worth being explicit about it.

The instinct is to take the new value, shift it into position, and OR it into the register. Like this:

// WRONG. This is the bug. ctrl |= (new_mode << 5);

The problem is that OR can only flip bits from 0 to 1. It can't flip them back. So if the MODE field already had some bits set, those bits stay set, and you end up ORing the new value on top of the old one. The result is whatever bits were in either, not the new value.

To change a field reliably, you have to clear it first, then OR in the new value. The pattern is clear, shift, OR.

ctrl &= ~(0x7 << 5); // 1. clear bits 5-7 ctrl |= (new_mode & 0x7) << 5; // 2. insert new value into bits 5-7

The first line builds the mask 0x7 << 5, which is 0b1110_0000. Then it inverts it, giving ...1111_1111_0001_1111. Then it ANDs that with ctrl, which clears just those three bits and leaves everything else alone. The second line takes the new value (masked to three bits for safety, in case the caller passed something bigger), shifts it into place, and ORs it in.

You'll see this pattern in every embedded driver you ever read. Sometimes it's compressed into a single line, like ctrl = (ctrl & ~(0x7 << 5)) | ((new_mode & 0x7) << 5). Same idea. Same three steps.

Clear, then OR. OR alone can only set bits. To change a field, you have to clear it first.

Why this matters for embedded ML specifically

Two reasons this isn't an aside.

First, you'll use peripherals constantly. Configuring DMA to move tensors from one memory region to another. Setting up a timer to trigger inference at a fixed rate. Reading from an ADC to feed sensor data into your model. Configuring SPI or I²C to talk to an external sensor or accelerator. All of this is register-level work, and all of it lives in datasheets that look exactly like the CTRL example above.

Second, the moment you integrate a neural network IP block — a Coral Edge TPU, an Ethos-U55, a Hexagon DSP, a custom NPU — its datasheet describes how to drive it through registers. Layer dimensions, weight memory addresses, quantisation parameters, output destinations, start/stop control. All of it is register fields. If you can't read those layouts, you can't drive the accelerator. You'll be stuck calling vendor libraries and hoping they do what you think they do.

This isn't optional for the kind of role you're aiming at. It's table stakes.

One last thing that confuses people

Endianness and register bit numbering operate at different levels, and it's worth saying that explicitly.

When a datasheet says "bit 31 is the most significant bit and bit 0 is the least significant", that's about bits inside a register's value, not about bytes in memory. Inside a 32-bit register, bit 31 is always the MSB. That's universal. Endianness only changes the order in which the four bytes of that register's value appear when you treat memory as raw bytes.

So when you write (reg >> 0) & 1 in C, you get the LSB of the register's value, regardless of endianness. The C compiler handles the byte ordering for you. You only have to think about endianness when you treat memory as a sequence of raw bytes — like reading from a file, doing DMA, or interpreting a network packet — not when you're treating it as typed values.

Where this lands

Three takeaways.

Endianness is the byte-order convention for multi-byte values in memory. Little-endian puts the low byte at the low address. Big-endian puts the high byte at the low address. Almost everything you'll touch in embedded ML is little-endian, but big-endian shows up in network protocols and some file formats. Memory dumps on little-endian chips look "backwards" relative to the value's normal hex notation, and you have to mentally reverse them.

Int8 quantised models are endianness-immune, because each storage unit is exactly one byte. This is one of the quiet practical wins of int8 for embedded inference.

Register layouts pack many fields into one word. Each field has a position and a width. To read a field, shift down then mask. To write a field, clear-then-OR. OR alone cannot change a field that already has bits set. This pattern is the backbone of every embedded driver you'll ever look at.
