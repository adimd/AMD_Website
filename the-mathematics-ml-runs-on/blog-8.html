The Mathematics ML Runs On · Class 8

The Space Too Big to Search

Counting asks one simple question: how many different things can happen? The answer explodes so fast that even a toy problem has more possibilities than there are atoms in the universe, far too many to ever try one by one. That explosion is the obstacle this whole class is about, and it is the reason a model learns by following a slope instead of testing every answer.

The answer you can't reach by trying

Here is the most obvious idea in all of machine learning, and the first one to die. To find the best model, try every possible setting, score each one, and keep the best. It needs no calculus and no cleverness, and it cannot fail to find the best answer, because it looks at all of them. The only real question is how many settings there are to look at.

A model is a row of on/off switches, each switch one yes/no setting. A real model has billions of settings, each far finer than on/off, but a single switch is enough to find the pattern. One switch has exactly two settings, off or on: two possibilities.

Now add a second switch. For each setting of the first switch, the second can still be off or on, so the possibilities are off-off, off-on, on-off, on-on: four of them. Add a third switch and each of those four splits in two again, giving eight. Each switch added doubles the count:

Each switch you add doubles the count

That doubling is the whole engine, and it never lets up. After n switches the count is 2 multiplied by itself n times, written 2n. Ten switches is already 1,024 combinations. Twenty is more than a million. Each step doubles everything before it.

The number of settings is only half the story; for "try them all," what matters is the time, and the time comes from one rule. Each setting takes one check, and the chip manages a billion checks, 109, every second. So the time is simply the number of settings divided by a billion, then read back in seconds, days, or years. Apply that one rule down a range of sizes:

Time to try every setting = (settings) ÷ (a billion per second)

Every row is the same division; only the input grows. And the last row is the one to sit with: the 1.3 × 1021 seconds for 100 switches dwarf the age of the universe, about 4 × 1017 seconds, by a factor near 2,900. A faster chip does not rescue the plan either, because the rule is a division: doubling the checking speed halves the time, which removes a single switch from the wall, and the next switch added doubles the count straight back.

The most natural plan in the whole field is ruled out before we write a single line of training code, and the thing that rules it out is counting: the plain arithmetic of how many possibilities there are.

Before we can talk about the chance of an outcome, we have to answer something simpler and stranger: how many outcomes are there even?

Class 7 put probabilities on outcomes and multiplied them together, but it quietly assumed we already knew what the outcomes were and how many of them existed. Probability begins one step before that, with counting. This class builds the four tools that let you measure the size of a space of possibilities, each from first principles: the sample space, the multiplication principle, permutations, and combinations. Every one of them, the moment you push it, explodes, and that explosion is the real lesson.

Section 1 · The sample space: the set of everything that can happen

Counting measures the size of a space of possibilities, so before we can measure one we have to name it. That space has a name of its own, and it is the most basic object in all of probability.

A sample space is the set of everything that can happen

Flip a coin. Exactly one of two things happens, heads or tails, and nothing else is possible. That complete list, written as a set {heads, tails}, is called the sample space. Roll a die and the sample space is {1, 2, 3, 4, 5, 6}. A set counts as a sample space when every possible outcome is in it, and exactly one of them happens on any given try, never none and never two at once.

It is a set, the Class 6 object, and for counting the only thing we care about is its size, written |S|. A coin has |S| = 2, a die |S| = 6. Easy here; the whole class is about cases where the size is the hard part.

The sample space is the set of possible outcomes, and we count its size

The chip's sample space: why a read has exactly 4096 outcomes

Now the hardware. When the ESP32 reads its light sensor, what is the sample space? The voltage at the pin is a real number, a point on Unit 1's infinite line, so you might expect infinitely many outcomes. But the lesson of Unit 1 was that the real line does not fit in a machine. The chip's analog-to-digital converter, its ADC, deals with that by quantizing: it keeps only a finite ladder of voltage levels and reports the nearest rung. The read is never a real number; it is always one rung of a finite ladder.

How many rungs? That is fixed by the bit count, and it is exactly the doubling from the opening. Each level is labelled by a pattern of bits, and with 12 bits, each off or on, there are 212 = 4096 patterns, so 4096 levels. The 4096 is nothing special, though; it is only the number for a 12-bit ADC. An 8-bit ADC has 28 = 256 levels, a 10-bit one 210 = 1024, a 16-bit one 216 = 65,536. The size of the sample space is just 2 raised to whatever the bit count happens to be. For the 12-bit reads this series uses, that set is {0, 1, 2, …, 4095}, with |S| = 4096.

A continuous voltage, snapped to one of 2¹² = 4096 levels

This same 4096-element set is what the probability course will later spread sensor-noise probabilities across. We have done no probability yet, only counted the set it will live on.

why this matters for ML

In a model the sample space is not an abstraction; it is a concrete thing with a size you can point at, and that size fixes the shape of the model itself. An image classifier that sorts pictures into 1,000 categories has a sample space of 1,000 outcomes, and its output layer is exactly 1,000 numbers wide, one probability per outcome. A language model's sample space at each step is its vocabulary, so a model with a 50,000-token vocabulary produces 50,000 probabilities every time it predicts a single word. The size of the sample space is literally how many probabilities the model has to compute, and add up to one, at every step.

That size also sets the difficulty before any learning begins. Spread evenly over 50,000 tokens, a blind guess gives each one a chance of 1/50,000, and the model's entire job is to pull probability off the 49,999 wrong words and pile it onto the right one. A larger sample space is a harder target, and the only way to know how hard is to count it. Measuring the size of the set is step zero of everything Class 7 did with probabilities. From here the sets grow far too large to write out, and the rest of this class is the machinery for measuring their size without listing a single element.

Section 2 · The multiplication principle: counting in stages

Section 1 measured a single sample space: one read, 4096 outcomes. But a single choice is never the interesting case. A model is thousands of settings stacked together, a sentence is many words in a row, a dataset is many examples at once. The spaces that matter, and the spaces too large to ever list, are all built by combining many smaller choices. Which raises the question that unlocks every one of them:

If every choice on its own has only a handful of options, how large is the space of all of them combined?

We have already leaned on an answer to this, on faith. In the opening, every switch we added doubled the count, and we let that pass without asking why a new choice should double the total rather than add a couple to it. Settling that is the whole of this section, and the answer turns out to be the single engine behind every explosion in the class: a way to read the size of a combined space straight off the sizes of its parts, without ever listing one combination.

Why two stages multiply

Take 3 shirts and 2 pairs of trousers, and count the outfits. Go through the shirts one at a time. The red shirt goes with either pair of trousers, so it makes 2 outfits. The blue shirt makes 2 more, and the gray shirt 2 more, which is 2 + 2 + 2 = 6. Adding the same 2 once for every shirt is exactly what multiplying is, so the count is 3 × 2 = 6.

Every pairing is one cell of a grid: 3 × 2 = 6

When a thing is built from stages, and each stage has its own number of options, the size of the whole space is the options at each stage multiplied together.

Now the two sensor reads. The first read can be any of 4096 values, and for each one the second read can again be any of 4096, which is 4096 rows and 4096 columns of that same grid: 4096 × 4096 = 16,777,216 possible pairs. This is the multiplication that combined probabilities in Class 7, pointed at counts instead of chances: when the stages do not affect each other, the totals multiply.

Two quiet conditions sit inside that word "multiply," and both decide what the later sections look like. The first is independence: each read still has all 4096 values open no matter what came before. The moment a choice removes options from the next stage, say you are dealt cards and cannot draw the same one twice, the clean product breaks and turns into a product of shrinking numbers, which is all of Section 3. The second is that this count is ordered: the pair (12, 80) is counted separately from (80, 12), because reading 12 then 80 is a different record from reading 80 then 12. Whether order ought to count is the hinge between the next two sections, permutations and combinations. For now both hold, so the plain product stands.

Repeat a stage and the count becomes a power

When the same choice repeats, the product turns into a power. Read the sensor n times and the number of possible records is 4096 multiplied by itself n times, 4096n. In general, n independent stages each with k options give kn.

That one formula is behind everything so far. The opening's switches were k = 2 options (off or on) over n stages, which is 2n. Section 1's ADC was a single read labelled by 12 bits, each with 2 options, which is 212 = 4096. Both are the multiplication principle with the same choice repeated.

This is nothing like adding, and the difference is the whole reason these numbers leave the page. A hundred switches counted one at a time feel like a hundred small things, so the instinct is that the work is about a hundred-sized. But each switch multiplies the running count instead of adding to it, so the total is 2100, not 200. Addition only accumulates; multiplication compounds, stacking a fresh factor on top of everything already there at every single step. A linear cost you can outrun with a faster chip; a compounding one you cannot.

why this matters for ML

The multiplication principle runs a chore every practitioner meets on day one. Tuning a model means trying combinations of settings, and combinations multiply: 4 learning rates, 3 batch sizes, and 5 architectures is not 12 experiments but 4 × 3 × 5 = 60, and adding a single five-way knob makes it 300. A full grid search blows up the moment there are more than a handful of knobs, which is exactly why nobody runs a complete one and why random and guided search took its place.

The repeated-power case is why a language model never lists its answers. A sentence of just 20 tokens drawn from a 50,000-word vocabulary is one of 5000020 possible sentences, about 1094, more than the atoms in the universe. There is no table of them to pick from. The model cannot choose a sentence by enumerating the options, so it does the only thing left: it spreads a probability across that sample space and draws from it, one token at a time. The size we just counted is the exact reason Class 7's probabilities are unavoidable.

Section 3 · Permutations: when the order matters

So far the choices at each stage were the same every time, all 4096 of them, all reusable. Now change one thing: line up n distinct things in a row, where each can be used only once. How many different orders are there?

The multiplication principle still answers it, you just have to notice that the number of choices shrinks at each stage. For the first slot in the row, any of the n things will do. For the second slot, one is already placed, so only n - 1 remain. For the third, n - 2, and so on down to the last slot, where exactly one thing is left. Multiply those stage counts together: n × (n-1) × (n-2) × … × 1. That product is common enough to earn its own name and symbol, n factorial, written n!.

Three letters A, B, C make it concrete: 3 choices for the first slot, 2 for the second, 1 for the last, so 3 × 2 × 1 = 6 orderings, and you can list every one.

The 6 orderings of A, B, C, built slot by slot

If you only fill r of the n slots, you stop the shrinking product early, after r factors: that is a permutation of r from n, equal to n! / (n-r)!. But the headline is what happens to the full n! as n grows, because it is the fastest-climbing thing in this entire course.

Fast enough to break the machine almost immediately, which is the Unit 1 lesson coming back around. A factorial is a count, a whole number, so it lives in an integer type, and integer types have a ceiling (Class 4). A 32-bit unsigned integer tops out near 4.3 × 109, and 13! already sails past it. A 64-bit unsigned integer, the largest ordinary integer the chip has, tops out near 1.8 × 1019, and it survives only to 20!. At 21! the true answer is about 5.1 × 1019, the integer overflows, and the stored count is silently wrong.

The count of ways to arrange just 21 things does not fit in the widest integer the processor offers. Push to a shuffled deck of cards, 52!, and the number is about 8 × 1067: every properly shuffled deck in history has, with overwhelming probability, never appeared before and never will again. why this matters for ML

Permutations are the count of orderings, and orderings show up wherever sequence matters: ranking a page of search results, ordering the words of an output, scheduling operations. The lesson is rarely that you should compute a permutation; it is that you must never try to enumerate one. The number of orderings of even a short list is past the machine's largest integer, so any method that hopes to "look at all the orders" is dead on arrival, the same wall as the opening's hundred switches.

Section 4 · Combinations: when the order doesn't matter

One more twist, and it is the one machine learning leans on most. Pick a mini-batch of k training examples out of a dataset of N. The batch made of examples {3, 9, 40} is the exact same batch as {40, 3, 9}; the order you grabbed them in means nothing. How many distinct batches are there?

It is almost the permutation count, but with one correction, and the correction is itself a small multiplication-principle argument. If you counted orderings, you would count the batch {A, B} twice, once as A B and once as B A. In general a group of r chosen things can be internally ordered in r! ways, and the permutation count includes every one of them separately. Since order does not matter here, all r! of those are the same choice, so you divide them out:

combinations = (the ordered count) ÷ (the orderings you double-counted) = n! / ( r! × (n-r)! )

Watch the correction on small numbers. Choose 2 from {A, B, C, D}. As ordered pairs there are 4 × 3 = 12. But each unordered pair was counted twice, so the real number of pairs is 12 ÷ 2 = 6.

12 ordered pairs collapse into 6 unordered ones

This count is written C(n, r) and read "n choose r." It grows just as wildly as the factorial it is built from. The number of 5-card poker hands is C(52, 5) = 2,598,960, still countable. But the number of ways to choose 50 items from 1000 is about 9 × 1084, and the number of distinct 32-example mini-batches from a 60,000-image training set is around 10117. why this matters for ML

Combinations count the subsets, and ML is built on subsets: which examples land in a mini-batch, which neurons a dropout layer switches off this step, which rows go to training and which to test, which features a tree considers. The number of possible subsets is so enormous, that 10117 of mini-batches, that no run could ever sweep through them. So training does not choose subsets by enumerating them; it draws them at random, trusting that a random sample stands in for a whole it can never list. The combination count is the proof that random sampling is not laziness but necessity.

Section 5 · Why the space is too big to search, and what that forces

Step back and put the four tools together. They all do the same thing: they measure the size of a space of possibilities, and that size, every time, is enormous beyond use. The opening's hundred switches were 2100. A model of just 40 bytes, each a value from 0 to 255, has 25640 = 2320 ≈ 2 × 1096 possible settings, which is larger than the roughly 1080 atoms in the observable universe. The space of a tiny model is bigger than the physical universe, and the number describing its size would itself overflow the machine, exactly as 21! did.

A 40-byte model's space sits past everything physical

Two consequences follow, and between them they shape almost everything the course does next.

The first: you cannot find the best model by trying every model. The space is not large, it is unsearchable, and no hardware closes that gap. So training does the opposite of enumeration. It starts at one setting, measures which direction lowers the loss, and steps to a better neighbor, over and over, never seeing more than a thread through the space. That is gradient descent, and the reason it exists at all is the counting in this class. It is also where Class 9 picks up: a search that cannot list its options can only move step by step and hope it settles, which is a question about sequences and limits.

The second: you cannot list every outcome in order to reason about it either. A 20-token sentence is one of 1094; you will never tabulate them. So instead of a list you carry a probability spread over the sample space, the move from Class 7, which lets you say something about a whole space you can never walk through one element at a time. Counting is what tells you the walk is hopeless, and probability is the tool you reach for once you accept that.

why this matters for ML

Counting is not a side errand before the real mathematics; it is the proof that the two pillars of the field are necessary rather than optional. Because the space of models is unsearchable, learning must be an iterative climb instead of a search, which is optimization. Because the space of outcomes is unlistable, reasoning must be done with probabilities instead of enumeration, which is statistics. Every later class stands on the fact this one establishes: the things that can happen are too many to try.

What to carry out of Class 8

The sample space is the set of every outcome that can occur, and the first thing to know about it is its size. The multiplication principle says independent stages multiply, so n choices of k options give kn, the same multiply that combined Class 7's probabilities. Permutations count orderings and equal n!, which overflows a 64-bit integer at n = 21. Combinations count subsets, n! / (r! (n-r)!), by dividing out the orderings you do not care about. And the single idea under all of them: these counts explode past the machine and past the universe, which is precisely why machine learning follows slopes instead of trying every answer, and reasons with probability instead of listing every outcome.
