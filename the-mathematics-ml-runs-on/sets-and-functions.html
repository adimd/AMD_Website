The Mathematics ML Runs On · Class 6

The Function That Has No Formula

Unit 2 builds the language the rest of the course speaks. Its very first word is "function," and almost everyone arrives carrying a version of it that is too small. This class trades it for the right one, the version that a lookup table, a trained neural network, and a coin flip all turn out to share. We get there by asking, at each step, one plain question: what does a function actually have to give you?

A task you have already done

Let me start with something concrete, because the whole idea of this class hides inside it.

You have a brightness value, an integer from 0 to 255, and you need to correct it for the way human eyes perceive light. This is gamma correction, and the standard recipe is a formula: scale the value into the range 0 to 1, raise it to a power, scale back.

the formula waycorrected = powf(raw / 255.0f, 2.2f) * 255.0f;

On a laptop, fine. On the ESP32-C3 from Unit 1, this is a problem, and you already know why: that chip has no floating-point unit, so powf is not one instruction, it is a slow software routine. Run it on every pixel of a stream and you fall behind. So you do the thing embedded programmers always do. You notice there are only 256 possible inputs in the first place. You compute the answer for all 256 of them once, before the program ever runs, and you store them in an array:

the table way: compute all 256 answers once, then never againuint8_t gamma[256] = { 0, 0, 0, 1, 1, 2, 2, 3, /* ... */ 255 }; corrected = gamma[raw]; // just a memory read now. no math at runtime.

Two ways to land on the same corrected brightness. One computes the answer when asked. The other looks it up from a table you filled in ahead of time. Sit with that pair for a second, because I am going to ask one question about it, and the answer quietly reorganizes how you read a great deal of code and, later, a great deal of machine learning.

The powf version is obviously a function. Is the table a function too, or is it "just data"?

Most people's gut says the table is just data. A function, surely, is something with an x in it, a rule you carry out. The table has no rule anywhere; it is a frozen list of answers. Hold that instinct up to the light, because we are about to find it is wrong, and the wrongness is exactly what makes a neural network look mysterious when it should not.

Section 1 · A function is a commitment, not a formula

Drop the definitions for a moment and ask the only question that matters to whoever calls these two things: what do you actually get back?

You call powf(...) with raw = 100. You get one specific number. Call it again tomorrow with 100, you get the same number, never "it depends." Now you read gamma[100]. You get one specific number, the same one every single time. Stand at the call site and squint: the two are indistinguishable. Same input in, same single answer out, every time. The only difference is when and how the answer was produced, computed on the spot versus computed in advance and remembered. That is a question about speed and memory, which is a Unit 1 question. It says nothing about what kind of object you are dealing with.

So strip away the recipe, and the thing both versions truly provide is this:

A function is a promise: give it an input, and it hands back exactly one definite output, the same one every time. How it keeps that promise, by a formula, by a stored table, or later by learned weights, is a separate matter entirely.

Look again at f(x) = x2 with this in mind. The squaring is a recipe: it is the method this particular function uses to work out which output goes with a given input. But the recipe is not the function. The function is the full set of pairings, every input tied to its one output, and x2 is merely a compact way to describe those pairings. Replace the recipe with a giant table of precomputed squares and you have thrown away the formula while keeping every pairing intact. The function is exactly as real as before. It never lived in the formula; it lived in the pairings, and the formula was just one convenient way to write them down.

Once you believe that, the useful mental picture stops being a little machine grinding x into x2 and becomes two collections of things with arrows between them. On the left, every input the function is responsible for. On the right, every output it can produce. The function is the bundle of arrows: exactly one leaving each input on the left, landing on its committed output on the right. We name the two collections and write the whole thing compactly:

read aloud: "f, from A to B"f : A → B

A is the domain, the set of inputs the function must handle. B is the codomain, the set its outputs are drawn from. For our gamma function, both happen to be the bytes 0 to 255, so its signature is gamma : {0, …, 255} → {0, …, 255}. The powf version draws those 256 arrows by computing them; the table draws the identical arrows by storing them.

Same arrows, two ways to keep the promise

why this matters for ML

This is the picture every machine-learning object is built on, and the gamma table is the doorway. The embedding layer that begins almost every language model is, literally, a lookup table: hand it a token's id, it returns the stored row of numbers for that token, embedding[id], no formula in sight. It is gamma[ ] wearing a different hat. And a whole trained network is a function too, taking an input vector to an output vector, with no formula a human could write; it is defined by a pile of learned numbers, exactly the way the gamma table is defined by stored numbers. Insist that a function must be a formula and all of this looks like sorcery. Accept that a function is a committed map from inputs to outputs and it becomes readable: some maps are computed, some stored, some learned, and they are all the same kind of thing.

Section 2 · The one rule, and the one freedom

We said "exactly one definite output per input." Those words quietly grant one freedom and forbid one thing, and people routinely mix up which is which. Rather than assert the rules, let me show them to you in the most literal function-as-a-table a programmer has: a dictionary.

Here is a tiny image classifier, written by hand as a dictionary from filename to label:

a dictionary is a function with a finite, listed domainlabel = { "img1.jpg": "cat", "img2.jpg": "cat", "img3.jpg": "dog", "img4.jpg": "dog", } label["img1.jpg"] # -> "cat"

This dictionary is a function: its domain is the four filenames, its codomain is the two labels. Now read two facts straight off it, because the dictionary makes both unmissable.

The freedom: many inputs may share one output. Two different keys, "img1.jpg" and "img2.jpg", both map to "cat". Nobody bats an eye; that is just an ordinary dictionary. This pattern has a name we will need, many-to-one, and you have seen it all over Unit 1 too: in a gamma table gamma[0], gamma[1], and gamma[2] are often all 0, and sign(x) sends every negative number to the single value -1.

The prohibition: one input may never have two outputs. Try to express the opposite and the language stops you. You cannot list "img1.jpg" twice with two different values; a dictionary key holds exactly one value, and a second assignment just overwrites the first. There is no way to say "img1 is both cat and dog," and there is no such thing as a function that does it either. That is the single rule a function cannot break, and your data structures enforce it for free.

So the test for "is this a function" is never "does it have a formula" and never "is each output unique." It is only this: does every input land on exactly one output. Here is that exact dictionary as a map; click a key to see its one arrow, and use the button to try to break the rule.

The dictionary, drawn as a map

Click any key on the left to see the single arrow it sends. Keys img1 and img2 both point to "cat": many keys sharing one value is an ordinary dictionary, and an ordinary function.

why this matters for ML

Many-to-one is not a flaw to put up with. It is the job. A real classifier takes millions of different cat photos, each one a distinct input, and sends them all to the single output "cat." That collapse, dropping the pose and the lighting and the background while keeping only the label, is exactly what you want it to do. The argmax at the end of a network works the same way: many different score vectors, one winning class. And the prohibition is why a trained model is deterministic at inference: feed it the same input and you get the same answer every time, because a single input pointing at two outputs would not be a function at all. At this level, "a model generalizes" is just many-to-one said in plainer words.

Section 3 · Sets: pinning down what is even possible

Every arrow we have drawn starts in a collection on the left and lands in a collection on the right. We have been waving at those collections loosely, "the inputs," "the labels." Let me show you why loose is dangerous, with a bug you could ship this week.

You read a sensor that reports a status, and the datasheet lists the possible values. You write the handler:

switch (status) { case OK: /* ... */ break; case STALE: /* ... */ break; case OVERTEMP: /* ... */ break; } // you forgot FAULT. one day it arrives, nothing matches, and the code falls through.

This bug is not in your logic. It is that you never wrote down, exactly and completely, the collection of values status is allowed to be. You kept a fuzzy copy in your head, it was missing one, and nothing checked you. The fix is to name that collection precisely, every value, no duplicates, nothing left out. That precise collection is a set:

S = { OK, STALE, OVERTEMP, FAULT }

And here is the one idea to take from this section, the thing a set actually is for our purposes:

A set is the exact answer to "what values are even possible here?" That is precisely what a domain and a codomain are: the set of possible inputs, and the set of possible outputs.

Once the possibilities are nailed down as a set, three questions you ask constantly stop being guesses and become exact. Let me take them one at a time.

1. Is a given value in the set? Membership is strictly yes or no: a value is in the set or it is not, written FAULT ∈ S and 99 ∉ S. That yes-or-no test is exactly what your switch is meant to answer for every element, and the bug was simply one membership case you never handled. A good compiler will warn you on a non-exhaustive switch over an enum for this reason: the enum is the set, and the compiler is checking that your function covers all of it.

2. How many values are in it? The count of distinct elements is the set's cardinality, written |S|. Here |S| = 4. This sounds trivial until it reaches back and grabs Unit 1: a uint8_t is, as a set, the values from 0 to 255, so |uint8| = 28 = 256. That is not a new fact; it is the same 256 patterns from the wrap-around clock of Class 5, now named as the size of a set. A 12-bit ADC reading is a set of size 212 = 4096.

3. Does one set sit inside another? This is the one I want to slow down on, because it is the most useful. There are two different sets in play, and the gap between them is the whole point. The small set is your four valid statuses. The big set is every value a byte can physically hold, all 256 of them. Every valid status is a byte, so the small set sits entirely inside the big set. We call that a subset and write S ⊆ {0, …, 255}.

Now the danger becomes precise. The hardware can hand you any value from the big set, any of the 256 bytes. Your code only handled some of them. A bug happens whenever a value arrives from the big set that your small handled-set left out, whether that is the legitimate FAULT you forgot or a garbage byte from a glitchy wire. "Unhandled value" bugs are, every single time, this exact shape: you handled a subset of what could actually show up.

why this matters for ML

That subset gap is the deepest idea in all of learning, under a different name. Your training data is a tiny subset of every input the world could ever present to the model. Training teaches the model to behave on that subset. But in production, inputs arrive from the big set, almost all of which the model never saw. Performing well on the part of the big set you never trained on is exactly what generalization means. It is the FAULT-fell-through gap again, promoted to the central problem of the field. And cardinality is on the first slide of every model too: MNIST has a label set of size 10, ImageNet 1000, and a language model's vocabulary V is a set whose size |V|, often above fifty thousand, fixes how big the embedding table and the output layer must be.

Section 4 · Reading a function by its signature

Here is a habit question. You open an unfamiliar codebase and land on a function you have never seen. Before you read a single line of its body, what do you look at to know how to use it?

Its signature: what it takes in, and what it gives back. int parse(const char *) already tells you the input set and the output set, and you can wire it into your code correctly before understanding one thing about how it works inside. A mathematical function carries the very same label, and we have already been writing it:

domain in, codomain out: a type signaturef : A → B

Reading a component by its signature, domain to codomain, is the fastest way to navigate machine learning, because the signature tells you what plugs into what. Here are the pieces you will meet constantly, each one just a map from one set to another:

The signatures worth memorizing
  • image classifier
    Images → { cat, dog, … }
    many photos in, one label out
  • linear layer
    ℝn → ℝm
    an n-number vector in, an m-number vector out
  • argmax
    ℝk → { 0, 1, …, k-1 }
    k scores in, the index of the winning one out
  • embedding
    V → ℝd
    a token from the vocabulary in, its stored vector out

Read top to bottom and a model stops being a wall of code: it is a few maps, each with a clear set going in and a clear set coming out.

why this matters for ML

That last signature, the embedding V → ℝd, is worth seeing run, because it closes the loop of this whole class: a function with no formula, mapping a member of a set to a vector, by pure lookup. Pick a word below. Watch it become an index, which is just a position in the vocabulary set shown as a one-hot vector, and then the stored row of numbers that index points at.

Section 5 · Chaining maps, and why the shapes must line up

One function is rarely the whole story. You feed the output of one straight into the next. In code you have written this a thousand times:

do f, then feed the result to gh = f(x); y = g(h); // the same as y = g(f(x))

That is composition, written g ∘ f and read "g after f." It is the move a neural network is built from. But it only works under one condition, and that condition is the leading question of this section:

When is chaining two functions even allowed?

Exactly when the output of the first lands in the set the second takes as input. The arrows coming out of f have to arrive in the set that g's arrows start from, or g has nothing to act on. Said with signatures: if f : A → B and g : B → C, then the chain is g ∘ f : A → C, and the shared B sitting in the middle, the codomain of the first equal to the domain of the second, is the entire reason it holds together.

Composition needs a shared set in the middle

why this matters for ML

A neural network is a composition of functions. Each layer is a map, and the network is layers chained nose to tail, out = f3(f2(f1(x))). That one line is the architecture. And the shared-set rule is the very first error every practitioner meets: a shape mismatch. If layer one outputs a vector in ℝ128 but layer two expects ℝ256, the middle set does not match, the codomain of one is not the domain of the next, and the framework refuses to run. Drag the two dials and watch the seam meet and break:

When the dials match, the codomain of layer 1 equals the domain of layer 2 and the two maps fuse into one. When they differ, you get the shape error every beginner has stared at.

Zoom all the way out and the payoff of the class is one picture: a real model is just a row of maps, each with a clean signature, each handing its codomain to the next one's domain.

A model is a composition of maps

What to carry out of Class 6

We started with one honest question, is a lookup table a function, and the answer reorganized everything. A function is a promise of exactly one definite output per input, and the recipe that keeps the promise, a formula, a stored table, or learned weights, is a separate and lesser thing. Picture it as arrows from a domain to a codomain, where many inputs may share an output but no input may have two. The collections it connects are sets, which pin down what is even possible and let you ask precisely whether a value belongs, how many there are, and whether one set sits inside another, the same gap that separates a handled status from a stray FAULT and a training set from the world. Read every component by its signature, f : A → B, and remember that a model is just such maps composed, which is the entire reason the shapes have to meet in the middle.

The formula was never the function. The map is. Once a lookup table, a trained network, and a coin flip read as the same kind of object, an assignment of one definite output to each input, the rest of this course stops asking you to memorize and starts asking you to read.
