Understanding Memory in Microcontrollers

How Programs Occupy Memory: Sections, Placement, and Layout

A program’s memory structure is largely decided before it ever runs

In earlier discussions, we examined what occurs after a reset. Memory regions are cleared, predefined values are transferred into RAM, and a stack space is established. By the time execution reaches main(), the runtime environment appears fully formed. Variables behave predictably, and program logic proceeds as expected.

This naturally leads to a deeper question. How did these memory regions come to exist in the first place? Why do some variables belong to the .data space while others appear in .bss? Who determines where the stack resides? How does the system know which portions of memory must be cleared or initialized?

Before the program begins execution, its memory layout has already been designed.

A compiled program is not merely a sequence of instructions. It is also a structured description of how code and data should be arranged within the address space. The organization of memory is therefore not constructed arbitrarily at runtime. It is guided by decisions made during compilation and linking.

To understand this structure, we must shift perspective once again. Instead of asking how memory is initialized, we now ask how memory is partitioned. Instead of observing execution behaviour, we examine how the program’s components are positioned within the address space before execution even begins.

The key to this understanding lies in the idea of sections.

Why Sections Exist at All

To understand why programs are divided into sections, consider a simple thought experiment. Imagine placing an entire program into memory without any internal structure. Instructions, variables, constants, temporary data, everything written one after another into a single continuous region.

At first, this may seem perfectly reasonable. After all, memory is just storage. Why should it matter whether code and data are mixed together? The difficulty appears only when we examine how different parts of the program are expected to behave.

Suppose a variable is defined with an explicit starting value: 

int threshold = 10;

When the system powers on, threshold must begin with the value 10. But RAM cannot preserve values across resets. The initial value must therefore be stored somewhere persistent, such as Flash memory, and later written into RAM before execution begins.

Now consider another variable: 

int error_count;

This variable has no explicit initializer. Its defined starting state is zero. Storing thousands of explicit zeros in Flash would waste program memory. A far more efficient strategy is to simply reserve space in RAM and clear it during startup.

Already, two variables impose completely different requirements. One needs stored initial data. The other needs only reserved space and a clearing rule.

Different variables require different initialization strategies.

Instructions introduce yet another constraint. Program code must reside in non-volatile memory so that it survives resets. Unlike variables, instructions are not normally rewritten during execution and do not require runtime initialization.

Execution itself adds further complexity. Function calls create temporary state whose size and lifetime change continuously. This memory cannot be predetermined as fixed stored values.

If all program components were mixed indiscriminately, the system would have no reliable way to determine:

  • Which memory regions must be copied from Flash
  • Which regions must be cleared to zero
  • Which regions contain executable instructions
  • Which regions must remain available for dynamic execution
The system needs a way to distinguish memory with different behavioral rules.

Sections provide exactly this distinction. Instead of treating the program as a monolithic block, the build process classifies its components into groups that share similar storage and initialization requirements. These groups later guide how memory is arranged and prepared.

From Program Components to Named Sections

Let us make this classification process concrete by examining a very small program. Consider the following example: 

int limit = 5;
int count;

int main()
{
    int temp = limit;
    while (1) { }
}

Although this program is simple, it already contains multiple kinds of information that the system must treat differently. Each declaration imposes distinct requirements on memory.

The variable limit is defined with an explicit initial value. When the device powers on, this value must exist. Because RAM cannot retain values across resets, the number 5 must be stored in non-volatile memory as part of the program image.

The initial value of limit must be preserved in Flash memory.

Yet during execution, limit behaves like an ordinary writable variable. It must therefore occupy RAM. This dual requirement : persistent storage followed by runtime copying , places limit into the .data section.

Variables with explicit initial values are grouped into the .data section.

The variable count presents a different situation. No starting value is specified, but its defined initial state is zero. Storing large regions of zeros in Flash would be wasteful. Instead, the program simply reserves space in RAM and relies on startup code to clear it.

Variables that begin as zero are grouped into the .bss section.

Now consider the function body. The local variable temp is created only when main() executes. Its lifetime is temporary and tied to the flow of execution. Such storage cannot be handled like global variables.

Local variables are allocated from the stack region of RAM.

Even before the program runs, the build system has already recognized these differences. Instructions form one group, initialized variables another, zero-initialized variables another. These groups become the named sections of the program.

  • .text → executable instructions
  • .data → variables with stored initial values
  • .bss → variables cleared to zero at startup

Sections therefore do not emerge from naming conventions or toolchain preferences. They arise because different parts of a program impose incompatible memory expectations. Classification resolves these conflicts before execution ever begins.

Once this grouping is established, another question naturally follows. Knowing which components belong to which sections is only part of the story. Where are these sections actually placed within memory?

Who Decides Section Placement?

Once a program has been divided into sections, another practical problem immediately arises. These sections must occupy real addresses within the microcontroller’s memory. Instructions must reside in non-volatile memory. Variables must appear in RAM. The stack must be positioned within available space. None of these placements can be left ambiguous.

Source code alone does not specify physical memory addresses. A declaration such as int limit = 5; describes behaviour and intent, but says nothing about where the corresponding bytes should reside. The responsibility for transforming logical program structure into a concrete memory layout belongs to the linker.

The linker is the component that assigns addresses to program sections.

The compiler’s role is to translate individual source files into machine code and intermediate object data. At this stage, instructions and variables are organized into sections, but their final positions remain unresolved. Each section is still effectively floating within an abstract address space.

The linker resolves this indeterminacy. It combines all object files, merges compatible sections, and determines where each section should reside within the target memory map. This decision process is guided by rules describing the available memory regions of the device.

Consider a microcontroller containing Flash and RAM. Instructions cannot be placed arbitrarily into RAM, nor can writable variables reside permanently in Flash. The linker must therefore respect the physical constraints imposed by hardware while maintaining the logical structure defined by the program.

Section placement is constrained by hardware, but determined by the linker.

From the programmer’s perspective, this entire operation remains invisible. The program is written in terms of variables and functions, not memory addresses. Yet before execution ever begins, every instruction and every byte of data has already been assigned a precise location.

This raises a deeper question. How does the linker know which regions of memory exist, and what rules govern their usage?

Describing Memory to the Linker

For the linker to assign addresses, it must first understand the memory landscape of the target device. Unlike a general-purpose computer, a microcontroller does not present a single uniform memory region. Instead, it contains multiple physically distinct memories, each with different capacities and behavioural characteristics.

Flash memory stores instructions and persistent data. RAM supports writable variables and execution state. These memories occupy different address ranges and obey different constraints. The linker cannot infer these details from the program alone.

The linker must be explicitly informed about the device’s memory structure.

Consider a simple example. Suppose a microcontroller contains 256 KB of Flash and 64 KB of RAM. Instructions must be placed into Flash. Writable variables must reside in RAM. Without knowledge of these regions, the linker would have no basis for deciding where sections should be located.

This information is provided through a memory description, a specification that declares which memory regions exist, their sizes, and their address boundaries. Rather than being a property of the programming language, this description reflects the physical hardware organization of the device.

Memory descriptions bridge program structure and hardware reality.

Once the linker understands the available memory regions, it can map program sections accordingly. The .text section is directed into executable non-volatile memory. The .data and .bss sections are placed into RAM. Additional rules may govern alignment, ordering, and reserved areas.

From this perspective, the linker’s task becomes clearer. It is not merely merging object files. It is constructing a memory-resident representation of the program that obeys both software semantics and hardware constraints.

Having established how memory regions are described, we can now examine how sections are actually positioned within those regions.

Placing Sections Into Memory Regions

Once the linker understands both the program’s sections and the device’s memory map, the placement process becomes a constrained matching problem. Each section must be assigned to a memory region whose properties satisfy its behavioural requirements.

The .text section provides the simplest case. It contains executable instructions, which must persist across resets and be readable by the processor. These constraints naturally direct the section into non-volatile program memory such as Flash.

Executable code is placed into non-volatile memory.

The .data section introduces a more nuanced situation. Its variables require specific initial values, which must be stored persistently. Yet during execution, these variables must remain writable and quickly accessible. To satisfy both constraints, the linker places their runtime addresses in RAM while retaining their initial values in Flash.

Initialized variables live in RAM but originate in Flash.

The .bss section follows a different logic. Its variables require no stored data, only reserved space and a rule enforcing an initial value of zero. The linker therefore allocates space exclusively in RAM, leaving startup code responsible for clearing the region.

Zero-initialized variables occupy RAM without consuming Flash storage.

These decisions illustrate a key principle. Section placement is not an arbitrary arrangement but a direct consequence of memory behaviour. Persistence, writability, and access speed together dictate where program components must reside.

Importantly, the linker defines only the memory layout, not the initialization actions themselves. The runtime system later interprets this layout to perform copying, clearing, and stack establishment during startup.

With section placement understood, we can now examine how these regions appear within the address space as a coherent memory layout.

Visualizing the Final Memory Layout

After sections have been classified and placed into appropriate memory regions, the program assumes a concrete structure within the device’s address space. Although this structure is rarely visible during ordinary programming, it governs nearly every aspect of runtime behaviour.

Consider a typical microcontroller containing Flash and RAM. Flash holds executable instructions and any persistent data required for initialization. RAM holds writable variables and execution state. The linker arranges program sections across these regions according to their roles.

The .text section, containing machine instructions, resides entirely within Flash memory. The processor fetches instructions from this region during execution. Because instructions must survive resets, non-volatile memory is essential.

The .data section occupies two conceptual locations. Its initial values are stored in Flash as part of the program image, while its runtime addresses exist in RAM. During startup, values are copied from Flash into RAM, constructing the writable data region expected by the program.

The .bss section resides exclusively in RAM. No persistent storage is required because its starting state is established by clearing memory during reset.

The stack region is also carved from RAM, typically beginning near the upper boundary of available memory. Unlike static sections, the stack expands and contracts dynamically as functions execute.

All runtime data ultimately competes for space within RAM.

This layout reveals an important truth. Sections do not represent separate memories, nor independent storage mechanisms. They are organizational constructs describing how a single address space is populated across distinct hardware regions.

Once execution begins, the runtime system interprets this layout to perform initialization, manage stack behaviour, and support variable access. The memory map defined during linking thus becomes the foundation upon which execution unfolds.

With this structural view established, we can now explore the dynamic consequences of memory layout, how regions interact, how boundaries are crossed, and how failures emerge when assumptions break.

A More Concrete View of the Linker’s Perspective

Up to this point, we have described the linker as the component responsible for assigning addresses and arranging sections within memory. To make this process less abstract, it is useful to briefly examine the form in which memory information is presented to the linker.

A linker does not automatically discover the structure of a microcontroller’s memory. The available regions, their sizes, and their permitted access patterns must be explicitly declared. A typical memory description may resemble the following: 

MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 256K
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 64K
}

This declaration conveys physical constraints rather than program behaviour. Flash memory is marked as readable and executable, while RAM is designated as readable, writable, and executable. The linker now possesses a map of the device’s memory landscape.

Memory descriptions define what memory exists. They do not define what the program does.

With memory regions defined, section placement rules determine where program components should reside. These rules associate logical sections with physical memory regions: 

SECTIONS
{
    .text :
    {
        *(.text)
        *(.rodata)
    } > FLASH

    .data :
    {
        *(.data)
    } > RAM

    .bss :
    {
        *(.bss)
        *(COMMON)
    } > RAM
}

Even without examining every directive in detail, the intent is visible. Executable instructions and read-only data are directed into Flash. Writable variables are placed into RAM. Uninitialized storage is reserved within RAM without occupying Flash space.

Sections are steered into memory regions whose properties satisfy their runtime roles.

The linker therefore operates not as a passive combiner of files, but as a layout engine. It constructs a memory image of the program that simultaneously respects hardware boundaries and program semantics.

A Program’s Memory Is Designed Before It Runs

By the time execution begins on a microcontroller, the program’s memory structure is already defined. Sections have been identified, memory regions described, and addresses assigned. Runtime does not construct this layout; it operates within it.

Instructions reside where non-volatile storage permits persistence. Variables occupy RAM where writability and access speed are required. Regions that must begin as zero are cleared, while predefined values are transferred from program memory. Each behaviour follows directly from decisions made during compilation and linking.

Execution activates a memory organization that was determined in advance.

This perspective simplifies many aspects of embedded reasoning. Stack behaviour, dynamic allocation, memory limits, and failure modes are all consequences of how memory regions coexist within a fixed address space.

With this static view established, we can now examine the dynamic aspects of memory , regions whose usage evolves as the program runs.
