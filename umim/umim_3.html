Understanding Memory in Microcontrollers

The Address Space: How the CPU Sees Memory

{{BLOG_SUBTITLE}}

A Flat and Continuous Address Space

In the previous discussion, we looked at memory as a collection of regions with different roles. Program memory holds instructions, RAM supports runtime activity, and non-volatile storage preserves long-term data. From a programmer’s viewpoint, these categories feel like distinct parts of the microcontroller, each behaving in its own way.

Physically, this intuition is correct. These memory regions are implemented using different hardware structures. Flash memory, RAM, and peripheral registers are not the same kind of circuitry. They differ in speed, persistence, and internal design. Yet, despite these differences, the processor interacts with them through a remarkably uniform abstraction.

The CPU experiences memory as a single continuous space of addresses, even when the underlying hardware is diverse.

Instead of exposing separate memory systems, microcontroller architectures typically organize all accessible storage and control locations into one flat address space. This space can be imagined as a long sequence of numerical addresses, increasing in a predictable manner. Every location that the processor can access, whether it corresponds to RAM, Flash, or a hardware register , is assigned an address within this unified range.

This continuity is not accidental. It is a deliberate design choice. The goal is to simplify how the processor reads and writes information. From the instruction’s perspective, accessing memory always follows the same basic idea: operate on a specified address. The nature of the underlying hardware is hidden behind the address itself.

Different hardware components are mapped into the same address space so that memory access remains conceptually uniform.

An address, therefore, is simply a number from the CPU’s point of view. What that number represents depends entirely on how the system assigns meaning to ranges within the address space. One range may correspond to RAM, another to program memory, and yet another to peripheral control registers. The processor does not inherently distinguish between these categories during an access; it simply performs a read or write at the requested location.

This model explains why operations involving memory often appear so general. The same fundamental mechanisms are used to fetch instructions, manipulate data, and interact with hardware. The apparent diversity of behaviour emerges not from different access methods, but from how addresses are interpreted by the system’s design.

Viewing memory as a continuous address space is one of the most important mental shifts in embedded systems. Many mechanisms that initially seem unrelated such as pointer behaviour, memory-mapped I/O, linker decisions, and region-specific effects, are unified by this single idea.

Naturally, this leads to a deeper question. If memory is presented as a continuous space, how do different addresses produce different outcomes? Why does reading one address retrieve data from RAM while another may interact with a hardware peripheral?

The answer lies in memory mapping.

Memory Mapping: Assigning Meaning to Addresses

If the processor experiences memory as a continuous range of addresses, an obvious question arises. Why do different addresses behave differently? Why does writing to one location modify a variable in RAM, while writing to another may influence a hardware peripheral or access program memory?

The key idea is that an address, by itself, carries no inherent meaning. To the CPU, it is simply a number specifying a location. The behaviour associated with that location is determined entirely by how the microcontroller’s hardware is designed.

Memory mapping is the mechanism by which the system assigns purpose to ranges of addresses.

Inside the microcontroller, different hardware components are connected to the processor through an address decoding scheme. Certain address ranges correspond to RAM, others to Flash memory, and others to peripheral registers. When the CPU performs a read or write operation, the address value determines which physical component responds.

From the processor’s perspective, however, the operation itself remains conceptually identical. It issues a request involving an address. The system’s internal organization ensures that the appropriate hardware block interprets and services that request.

The same instruction format can interact with entirely different hardware depending only on the address involved.

This design provides a powerful simplification. Rather than inventing separate access mechanisms for memory and peripherals, everything is unified under the idea of addressable locations. A peripheral control register can be read or written just like an ordinary memory cell. The difference lies not in how it is accessed, but in what hardware is attached to that address.

In practical terms, this means that behaviour is encoded into the address space itself. Reading from a RAM address retrieves stored data. Reading from a Flash address retrieves program instructions. Reading from a peripheral-mapped address may instead reflect the state of a hardware device. The processor does not require special awareness of these distinctions.

Once this mapping concept is understood, many aspects of embedded systems become easier to reason about. Memory and hardware are no longer separate conceptual worlds. They are unified through addresses. The processor interacts with both using the same fundamental idea: access a location within the address space.

This naturally leads to another important realization. Instructions and data, despite appearing different at the programming level, are both accessed through this same addressing mechanism.

Code and Data as Addressed Entities

At the programming level, instructions and data feel like fundamentally different things. Instructions describe what the processor should do, while data represents the values those instructions operate upon. This distinction is entirely natural from a software perspective, yet the processor interacts with both through the same underlying mechanism.

From the CPU’s point of view, both code and data reside at addresses within the same continuous memory space. An instruction is fetched by reading from a specific address. A variable is accessed by reading from or writing to an address. The nature of the operation is identical. Only the interpretation of the retrieved bits differs.

To the processor, instructions and data are simply contents of memory locations.

When the program executes, the processor repeatedly reads from program memory addresses pointed to by the program counter. Each read retrieves a sequence of bits that the hardware interprets as an instruction. The act itself, however, is no different from reading any other memory location.

Similarly, when a program accesses a variable, the processor performs a read or write at the variable’s assigned address. The memory access mechanism does not change. The processor is not switching into a special “data mode”. It is simply interacting with another location in the address space.

The difference between code and data lies in meaning, not in the fundamental act of access.

This perspective helps explain why microcontroller memory systems can remain conceptually unified. The processor does not require separate conceptual models for instructions and values. Everything that can be accessed is represented as something located at an address. The interpretation of what is read is determined by context and hardware design.

Once this idea is internalized, an even more interesting implication emerges. If instructions and variables are both accessed through addresses, then hardware components themselves can also be represented within the same address space.

Memory-Mapped I/O: Hardware as Memory

Once memory is understood as a continuous address space, a very powerful idea emerges. Not every address corresponds to ordinary storage. Some addresses are connected directly to hardware components within the microcontroller.

Instead of treating peripherals as entities requiring special instructions, many microcontroller architectures map hardware control and status registers into the same address space used for memory. This means that interacting with certain hardware devices is performed using the same fundamental operations used to access RAM.

From the processor’s perspective, hardware can appear as memory.

A read or write operation targeting a peripheral-mapped address does not access a conventional memory cell. Instead, it communicates with a hardware module designed to respond at that location. Writing a value may configure a timer, change the state of an output pin, or trigger a peripheral action. Reading may retrieve the status of a device or reflect an external input.

The processor itself does not require a separate conceptual mechanism for these interactions. It issues a memory access involving an address. The memory mapping logic ensures that the appropriate hardware block responds. The uniformity of the address space abstraction is preserved.

The difference lies in what is connected to the address, not how the address is accessed.

This design greatly simplifies how the CPU communicates with the rest of the system. The same load and store operations used for variables can be used to control hardware. Peripherals become integrated participants in the address space rather than isolated subsystems requiring unique access rules.

This perspective also explains why certain memory operations have effects beyond data storage. Writing to one address might update a variable. Writing to another might change hardware behaviour. To the processor, both actions follow the same fundamental pattern: operate on an address.

With this, the address space abstraction reveals its full power. It unifies storage, instructions, and hardware control under a single conceptual model.

Pointers as Raw Addresses

With the idea of a continuous address space in place, we can now revisit one of the most important constructs in embedded programming: pointers. Pointers often appear intimidating because they are introduced through syntax and rules, rather than through the simple intuition that gives them meaning.

At its most fundamental level, a pointer is nothing more than a value that represents a memory address. Just as an integer variable holds a number, a pointer variable holds the numerical location of something within the address space. The processor does not treat this value as mysterious or special. It is simply another address.

A pointer is a variable whose content is an address.

Every object that exists in memory such as a variable, an instruction, a buffer, or a peripheral register, occupies some position within the address space. If a program can refer to that position numerically, it can indirectly access the contents of that location. This is precisely what pointers enable.

When a pointer holds an address, it is effectively identifying a location. Dereferencing the pointer instructs the processor to perform a memory access at that address. The mechanism is identical to any other memory read or write. The pointer merely provides the location dynamically rather than embedding it directly into the instruction.

Dereferencing a pointer simply means accessing memory at the address stored in the pointer.

This perspective dissolves much of the perceived complexity. A pointer does not contain data in the usual sense. It contains information about where data resides. It is an indirection mechanism, a way for the program to work with locations rather than fixed values.

The power of pointers comes from this indirection. Instead of operating only on known memory locations determined at compile time, programs can manipulate addresses as data. A pointer may refer to different locations over time, allowing flexible interaction with memory and hardware.

Seen from the address space viewpoint, pointers are not exotic features of the language. They are natural tools for working within a system where everything meaningful is located at an address. The program stores an address, then uses that address to access whatever resides there.

This also explains why pointers are central to embedded systems. Hardware registers, buffers, memory regions, and dynamically determined data structures are all accessed through addresses. Pointers simply allow addresses to be treated as manipulable values within the program.

The Illusion of Structured Memory

At the programming level, memory appears highly organized. We speak of variables, arrays, structures, and objects as though memory itself understands these distinctions. It is tempting to imagine that a block of memory somehow knows which bytes belong to which variable or what type of data is being stored.

The physical reality is far simpler. Memory is merely a sequence of storage locations. Each location holds bits. There are no intrinsic labels, boundaries, or types embedded within the hardware. What we perceive as structure is imposed entirely by how programs interpret those bits.

Memory contains bits. Meaning is assigned by interpretation.

A useful analogy is to imagine memory as a long row of identical boxes. Each box can hold a value, but the boxes themselves carry no indication of what the value represents. One program may treat a particular set of boxes as an integer. Another may interpret the same boxes as characters, instructions, or hardware control registers.

Nothing about the boxes changes. Only the interpretation does.

This perspective helps explain why memory can be viewed as fundamentally unstructured. The processor reads and writes values at addresses without any inherent awareness of programming abstractions. Concepts such as “variable” or “array” exist at the language level, not at the hardware level.

Structure is a contract between the program and the programmer, not a property of memory itself.

Consider a simple example. A group of consecutive memory locations may be interpreted as a number. The same locations could just as easily represent pixel data, sensor readings, or fragments of executable code. The underlying storage remains identical. Only the rules used to interpret the bits differ.

This idea is especially important when working with pointers and low-level operations. A pointer simply refers to an address. What resides at that address acquires meaning only through the program’s interpretation. Misunderstandings arise not because memory is complex, but because interpretation rules are violated or mismatched.

Once this illusion of intrinsic structure is set aside, many aspects of embedded systems become easier to reason about. Memory is a uniform substrate. Programs impose meaning. Hardware responds to addresses. The apparent complexity emerges from interpretation rather than from the storage mechanism itself.

Address Space as the Unifying Concept

At first glance, the internal organization of a microcontroller can seem like a collection of unrelated mechanisms. Program memory stores instructions, RAM holds runtime data, peripherals control hardware behaviour, and pointers appear as special language constructs. Each topic is often presented independently, which can make the overall system feel fragmented.

The idea of address space dissolves this fragmentation. Once memory is understood as a continuous range of addresses, many seemingly different concepts reveal themselves as variations of the same underlying principle. Instructions, variables, buffers, and hardware registers all occupy locations within this shared space.

Address space is the common language through which the processor interacts with everything inside the device.

The processor does not operate on abstract programming constructs. It reads from addresses, writes to addresses, and interprets the retrieved bits according to context and hardware design. Whether the address corresponds to RAM, Flash, or a peripheral is secondary to the act of access itself.

This perspective provides a remarkably stable mental model. Code execution becomes a sequence of memory reads. Variable manipulation becomes memory access. Hardware interaction becomes address-driven communication. Pointers become values containing locations. The diversity of behaviour emerges from interpretation, not from fundamentally different mechanisms.

Many embedded-system behaviours are best understood not as special cases, but as consequences of addressing.

Viewing the system through this lens also clarifies why certain programming constructs exist at all. Pointers are not arbitrary features of the language. They are natural tools for working with addresses. Memory-mapped I/O is not an unusual trick. It is a direct extension of the unified address model.

Once this unifying idea is internalized, reasoning about embedded software becomes more intuitive. Questions about variable placement, stack behaviour, peripheral access, and memory layout can all be reduced to a single guiding thought: what addresses are involved, and how are they interpreted?

With this foundation established, we are now prepared to explore how programs are arranged within this address space. Instead of asking how memory is accessed, we begin asking how memory is organized.
