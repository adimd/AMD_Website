Understanding Memory in Microcontrollers

From Reset to main(): How the Runtime Is Constructed

How embedded programs are prepared by the system before main() executes.

When writing embedded software, it is natural to imagine that a program begins its life at the first line of main(). After all, this is where the programmer’s logic appears to start. The function is visible, explicit, and central to the structure of most applications. Yet, from the microcontroller’s perspective, the story is very different.

A microcontroller does not power on into a running C program. It does not wake up knowing what variables exist, what functions have been defined, or what memory structures must be established. At the instant power is applied, the device is simply a processor with access to an address space. Nothing more is guaranteed.

Before main() executes, the system must first construct the very environment in which main() can exist.

This raises a subtle but profoundly important question. If RAM is volatile, if variables are abstractions of the language, and if execution requires a valid stack, how does a program ever begin running in a meaningful way? What prepares memory? What establishes state? What determines where execution starts?

To answer this, we must temporarily set aside the familiar view of programs as collections of functions and instead adopt the processor’s viewpoint. From the machine’s perspective, execution begins not with a function call, but with a reset event.

The Reset Event: Where Execution Truly Begins

From the programmer’s perspective, a reset may feel like a simple restart. The device turns on, the program runs, and execution appears to begin as though the system were resuming a familiar sequence. Internally, however, a reset is not a continuation. It is a reinitialization of the processor’s state.

At the moment of reset, the CPU does not possess awareness of functions, variables, or program structure. Those are constructs of the language and the toolchain. The processor operates on a far more primitive basis. It begins by fetching an instruction from a predefined location within the address space.

Execution begins with an address, not a function.

This starting location is determined by the microcontroller’s design. A specific address is reserved for reset behaviour, often referred to as the reset vector. When a reset occurs, the processor loads this address and begins instruction fetch just as it would for any other part of memory.

Nothing about this initial step implies the existence of a fully formed program environment. RAM contents are undefined. No stack has been established. No variables have been initialized. The processor simply begins executing instructions located at the reset entry point.

The program, as we recognize it, has not yet begun. Only instruction execution has.

What follows is a carefully orchestrated sequence of operations whose purpose is not application logic, but environment construction. Before meaningful program behaviour can emerge, memory must be prepared, runtime state must be established, and essential structures must be created.

In other words, the earliest instructions executed after reset are concerned not with what the program does, but with enabling the program to run at all.

Constructing Order from an Undefined State

Immediately after a reset, the processor begins executing instructions, but the surrounding memory environment is not yet meaningful. This is particularly important in the case of RAM. Unlike program memory, RAM does not retain its contents when power is removed. At startup, its state is undefined.

Undefined does not simply mean empty. It means that the values present in memory cannot be assumed to follow any predictable pattern. Residual electrical states, previous activity, or random conditions may influence what bits appear in each location. From the program’s perspective, RAM at reset is unreliable.

A program cannot begin reasoning with memory whose contents have no defined meaning.

Yet, high-level languages encourage a very different intuition. We write global variables, assign initial values, and expect those values to exist when execution reaches main(). This expectation is so natural that the underlying problem often goes unnoticed: RAM does not inherently know what values should be present.

The resolution of this mismatch is one of the primary responsibilities of the startup sequence. Before application logic can safely execute, memory must be brought into a predictable state. Certain regions must be cleared. Others must be populated with known values. Only then can variables behave as the programmer expects.

The runtime environment is not discovered at startup. It is constructed.

Some variables are expected to begin with zero values. Others are defined with explicit initial data. These expectations are not automatically satisfied by hardware. They must be established through explicit instructions executed before main() ever runs.

This early phase of execution is therefore less about performing computations and more about creating a stable universe in which computations can occur. Memory transitions from an undefined electrical state to an organized program state, enabling deterministic behaviour.

Two particularly important transformations occur during this process: regions intended to start at zero are cleared, and regions containing predefined values are initialized. Understanding these mechanisms reveals why variables appear to exist seamlessly when the program begins its visible execution.

Zeroing Memory: The Origin of Predictable State

One of the earliest responsibilities of the startup sequence is establishing a predictable baseline for memory. Certain variables are expected to begin execution with a value of zero. This expectation is deeply embedded in how programs are written, yet the hardware itself does not automatically guarantee such a state.

After a reset, RAM contents are undefined. If execution were to proceed directly into application logic, variables intended to start at zero could contain arbitrary values. The program’s behaviour would then depend on residual memory conditions rather than deterministic rules.

Predictable execution requires memory to be explicitly placed into a known state.

To enforce this predictability, the startup code deliberately clears specific regions of RAM before main() executes. Each location within these regions is written with zero. This is not an optimization or a convenience feature. It is a foundational requirement for reliable program behaviour.

Variables that belong to this category are those for which the program specifies no explicit initial value. Their defined starting condition is simply zero. Rather than storing zeros in non-volatile memory and copying them at runtime, the system performs a more efficient operation: it directly writes zeros into the relevant RAM region.

Memory is cleared because the program defines meaning, not because RAM begins empty.

From the programmer’s viewpoint, this process is invisible. By the time execution reaches main(), variables expected to be zero appear correctly initialized. The underlying mechanism — a sequence of memory writes performed during startup — is rarely observed unless one inspects the earliest stages of execution.

This clearing operation transforms part of RAM from an undefined electrical state into a deterministic program state. Only after this transformation can variables be safely assumed to hold meaningful values.

Not all variables, however, belong to this category. Some are defined with explicit initial values that must also be established before application logic begins.

Initializing Memory: How Values Appear in RAM

While some variables are expected to begin execution with zero values, others are defined with explicit initial data. A variable assigned a starting value by the program presents a very different challenge at startup. Unlike program memory, RAM cannot permanently store these predefined values across power cycles.

Yet, when execution reaches main(), such variables appear correctly initialized. Their values are already present, as though RAM had preserved them. The mechanism behind this behaviour lies in the cooperation between non-volatile memory and the startup sequence.

Initial values do not originate in RAM. They are transferred into RAM during startup.

The compiled program, stored in Flash memory, contains not only instructions but also the predefined data associated with initialized variables. Flash provides persistence, ensuring that these values remain intact even when power is removed. At reset, however, RAM contains no reliable representation of this data.

To reconcile this, the startup code performs a deliberate copying operation. A designated region of Flash, holding the initial values, is read sequentially. The retrieved data is then written into the corresponding locations in RAM. Through this process, the runtime memory image is constructed.

RAM is populated with meaning before application logic begins.

From the processor’s perspective, this operation is simply a sequence of reads and writes within the address space. But from the programmer’s viewpoint, it produces the illusion that variables have always possessed their assigned values. By the time main() executes, the transfer is complete and invisible.

This initialization step is fundamental to predictable program behaviour. Without it, variables defined with starting values would instead reflect undefined RAM contents, breaking the assumptions upon which the program’s logic is built.

At this stage, RAM has undergone two critical transformations. Regions requiring zero values have been cleared. Regions requiring predefined data have been populated. The memory environment is now approaching a state suitable for structured execution.

One essential component, however, is still missing. For functions to execute reliably, the program requires a valid stack.

Establishing the Stack: Creating Space for Execution

Even with memory cleared and initialized, the program is not yet ready for structured execution. High-level languages allow functions to be called, local variables to be created, and intermediate state to be maintained. These operations require a disciplined mechanism for managing temporary data during execution.

This mechanism is the stack. Despite its central role, the stack is not a pre-existing entity waiting inside the microcontroller. It is a region of RAM designated and prepared during startup to support function execution.

The stack is not a special hardware structure. It is a carefully managed area of memory.

When the processor resets, no valid stack context is guaranteed. The CPU may contain a reset-defined stack pointer value, but the memory region it refers to has not yet been meaningfully integrated into the program’s runtime environment. Before functions can safely execute, this pointer must refer to a known and appropriate memory location.

The startup sequence therefore performs another crucial step. It assigns the stack pointer to a predefined address within RAM. This address typically corresponds to the upper boundary of a reserved memory region. From this point onward, stack operations follow deterministic rules.

Stack behavior emerges from pointer movement within RAM.

Each function call, return address, and local variable allocation is implemented through systematic adjustments of this pointer. The processor does not “create” stack frames in an abstract sense. It simply reads and writes memory at locations relative to the stack pointer.

This explains why the stack is intimately tied to RAM usage. Stack growth consumes memory just like any other data structure. Excessive stack use or uncontrolled recursion does not trigger a graceful degradation. It risks overwriting adjacent memory regions, leading to unpredictable program behaviour.

From the programmer’s viewpoint, this entire process is invisible. By the time execution reaches main(), the stack appears as a natural component of the environment. Internally, however, it is the result of deliberate runtime construction.

With the stack established, memory initialized, and processor state prepared, the program environment is finally capable of supporting application logic.

Understanding RAM Through the Idea of Spaces

By the time execution approaches main(), RAM is no longer in the undefined state that exists immediately after reset. Portions of memory have been cleared, others initialized, and a region prepared to support function execution. Although RAM is physically a uniform resource, the runtime environment assigns distinct roles to different areas within it.

A useful way to understand this organization is to think of RAM as a collection of logical spaces. These spaces are not separate hardware structures. They are conceptual divisions imposed by the program to ensure predictable behaviour. Each space exists because the running system requires memory to serve different purposes simultaneously.

RAM is one physical memory, but the program treats it as multiple purposeful regions.

Some variables are defined with explicit initial values. These values are stored in non-volatile memory as part of the compiled program and must be transferred into RAM during startup. The region designated to hold such variables forms what is commonly referred to as the .data space.

The .data space holds variables whose initial values are defined by the program.

Other variables are expected to begin execution with a value of zero, despite having no explicit initializer. Instead of storing zeros in program memory, the startup sequence clears a dedicated region of RAM by writing zeros directly. This region becomes the .bss space.

The .bss space holds variables whose initial state is implicitly zero.

A third space supports an entirely different requirement. Function execution generates temporary state , return addresses, local variables, and intermediate data , whose lifetimes are tied to the flow of execution. This dynamic storage requirement is handled by the stack space, a region of RAM managed through systematic pointer movement.

The stack space holds the evolving context of function execution.

Although these spaces serve very different roles, they coexist within the same RAM. Their separation reflects logical organization rather than physical distinction. Understanding this layout is essential because interactions between these regions directly influence program behaviour and failure modes.

Seen from this perspective, terms such as .data, .bss, and stack do not describe different kinds of memory hardware. They describe how the runtime environment assigns meaning and responsibility to portions of a single memory resource.

A Concrete Example: Watching Memory Come Alive

To make these ideas tangible, consider a very small program. The goal is not to study language syntax, but to observe how different portions of memory must be prepared before execution reaches main(). 

int counter = 7;
int total;
 
int main()
{
    int temp = counter;
    while (1) { }
}

At the programming level, this example appears trivial. One variable is explicitly initialized, another is not, and a local variable is created inside main(). Yet from the system’s perspective, several carefully ordered operations are required before this logic can execute predictably.

The variable counter has an explicit initial value. That value must exist when the program begins execution. However, RAM cannot preserve values across power cycles. The initial value therefore resides in program memory as part of the compiled image.

The initial value of counter is stored in non-volatile memory and copied into RAM during startup.

The variable total, by contrast, has no explicit initializer. Its defined starting state is zero. Rather than storing zeros in Flash, the startup sequence clears the memory region assigned to such variables, ensuring that total begins with a predictable value.

Variables without explicit initializers are placed into a region that is cleared to zero at startup.

When execution finally enters main(), another memory space becomes active. The local variable temp is not stored alongside global variables. Its lifetime is tied to function execution, and its storage is allocated from the stack space established earlier.

Local variables are created by adjusting the stack pointer within RAM.

Despite the simplicity of the source code, the runtime environment has already performed several invisible transformations. Predefined values have been transferred from program memory. Certain RAM regions have been cleared. A stack region has been designated. Only after these steps does the program behave as the programmer expects.

This example illustrates an essential principle of embedded execution. A program does not merely start running. The memory universe it depends upon is actively constructed before visible logic begins.

Scope and Intent of This Discussion

The example above is intentionally minimal. Its purpose is not to exhaustively describe every memory region or runtime mechanism, but to build a clear mental picture of what must occur before main() can begin executing. Many important details have been simplified so that the underlying ideas remain visible rather than obscured by technical machinery.

In particular, we have focused only on the memory spaces required to understand basic runtime construction: initialized data, zero-initialized data, and the stack. These regions are sufficient to reveal the central theme of this chapter — that the execution environment is actively prepared by the system before application logic begins.

The objective here is to understand how a program becomes runnable, not to catalog every memory mechanism.

Readers familiar with embedded systems may notice the absence of another important region: the heap. This omission is deliberate. Dynamic allocation introduces additional concepts that are best explored after the foundational runtime model is firmly established. The heap, its behaviour, and its interactions with other memory regions will be examined in later discussions.

Similarly, terms such as .data and .bss have been introduced only at an intuitive level. Their precise definitions, placement rules, and relationships to the linker will be treated in much greater detail in subsequent chapters. For now, they serve as conceptual tools rather than formal technical constructs.

This chapter concerns what happens before main(), because that is where the runtime universe is constructed.

Once this perspective is internalized, later explorations of memory layout, linker behaviour, stack dynamics, and allocation strategies become far easier to reason about. The mechanisms differ, but the governing idea remains the same: memory state is engineered into existence.

Entering main(): When Program Logic Truly Begins

By the time execution reaches main(), the program is already running within a carefully prepared environment. Memory regions have been cleared, predefined values transferred, and a stack space established. What appears as the beginning of the program’s logic is, in reality, the continuation of a much earlier sequence of machine-driven events.

From the programmer’s viewpoint, main() represents the starting point of meaningful behaviour. From the processor’s viewpoint, it is simply another address within the instruction stream. The distinction is important. The system does not begin executing at main(); it arrives there only after constructing the conditions necessary for predictable execution.

main() does not create the runtime environment. It assumes its existence.

This explains why variables appear correctly initialized, why function calls behave consistently, and why execution proceeds deterministically. The runtime universe has already been assembled. Application logic now operates within a stable memory landscape rather than an undefined electrical state.

Seen from this perspective, the early stages of execution reveal an essential truth of embedded systems. Programs do not merely run on hardware. They depend upon a sequence of invisible preparation steps that transform raw memory into a structured computational environment.

Before program logic begins, memory must be made meaningful.

With this foundation established, we are now prepared to examine how these memory regions are defined, arranged, and managed. Instead of asking how execution starts, we turn to a complementary question: how does the program’s memory layout come into existence?
