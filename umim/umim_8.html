Understanding Memory in Microcontrollers

Global, Local, Static, and Const: How Variables Really Live in Memory

Understanding lifetime, visibility, and mutability from a microcontroller perspective

The Hidden Dimensions of a Variable

When writing programs, variables appear deceptively simple. They are introduced with a type, given a name, and used as though they were persistent entities within the system. From everyday programming experience, it is easy to assume that a variable is merely a labeled container for a value.

This intuition, while convenient, conceals several important properties that govern how variables actually behave in memory. Two variables with identical types may exhibit radically different lifetimes. Others may share the same lifetime yet differ in who can access them. Still others may occupy distinct memory regions despite appearing similar in source code.

A variable is defined as much by its behaviour as by its type.

To reason clearly about memory, it is useful to separate three independent dimensions that characterize every variable:

  • Visibility — Which parts of the program may access it
  • Lifetime — How long its storage must exist
  • Mutability — Whether its value is intended to change

These dimensions are rarely emphasized in introductory programming discussions, yet they determine where memory is allocated, how long it remains valid, and how the runtime environment manages it. Confusion surrounding keywords such as static and const often arises because these properties are implicitly intertwined in everyday thinking.

Scope, storage duration, and constness are separate ideas that happen to interact.

In the sections that follow, we examine familiar variable categories : local, global, static, and const , not as syntactic constructs, but as manifestations of these underlying memory behaviours.

A Small Program with Many Kinds of Variables

Let us begin with a very small program fragment. At first glance, nothing about it appears unusual. It contains a few variables, a function, and some simple assignments. 

#include <stdint.h>

int global_counter = 10;
const int system_limit = 100;

void example_function()
{
    static int persistent_value = 5;
    int temporary_value = global_counter;

    temporary_value++;
    persistent_value++;
}

Despite its size, this program already contains multiple categories of variables whose behaviour in memory differs fundamentally. Some values are expected to persist indefinitely. Others exist only briefly. Some may be modified, while others are intended to remain unchanged.

Variables that look similar in source code may follow very different rules at runtime.

Rather than introducing definitions immediately, it is more instructive to observe what the program implies. Each variable declaration quietly encodes assumptions about visibility, lifetime, and mutability. These assumptions, though rarely made explicit, determine how memory must be allocated and managed.

Consider the function example_function(). Every time execution enters this function, certain variables appear to come into existence. When execution leaves, some disappear. Yet others remain. Even without examining machine code or memory maps, we can reason about these behaviours directly from the program’s structure.

A variable’s lifetime is not determined by its type, but by how it is declared.

In the sections that follow, we use this single program to examine how different variables live in memory and why their behaviour can only be understood by separating concepts that are often conflated in everyday programming.

Temporary and Persistent Variables Inside a Function

Let us focus attention on the variables declared within example_function(). Two declarations appear side by side: 

static int persistent_value = 5;
int temporary_value = global_counter;

Syntactically, these statements look nearly identical. Both introduce an integer variable. Both associate a name with a value. Yet their behaviour during execution differs in a fundamental way.

Each time the function executes, temporary_value is created anew. Its existence is tied directly to the act of entering the function. When execution leaves the function, the storage associated with this variable is no longer needed and may be reclaimed immediately.

The lifetime of temporary_value mirrors the lifetime of the function call.

The variable persistent_value, however, follows a completely different rule. Although declared within the function, it is not recreated on each invocation. Its storage must exist independently of how many times the function executes. The value modified during one call remains visible in the next.

Conceptually, this variable behaves as though it were allocated once and then retained across executions. Entering the function does not create a new instance. Leaving the function does not destroy it.

The static declaration detaches lifetime from execution flow.

This contrast reveals an important principle. Variables declared within a function do not necessarily share the same lifetime. Some storage is governed by execution context. Other storage is governed by program lifetime.

The distinction is not cosmetic. It determines whether memory may be reused immediately after function return or must remain reserved indefinitely. It determines whether values naturally vanish or accumulate across calls.

To understand why this difference exists, we next examine variables whose lifetime is explicitly independent of any particular function execution.

Variables That Exist Without Function Execution

The program fragment introduced earlier also defines a variable outside any function: 

int global_counter = 10;

Unlike the variables inside example_function(), this declaration is not associated with a particular execution context. No function needs to be entered for global_counter to exist. No function return can destroy it.

Its storage must be available from the moment the program begins execution and remain valid for as long as the program continues to run. In other words, its lifetime coincides with the lifetime of the entire program.

A global variable exists independently of control flow.

This property has practical consequences. Any function may read or modify the variable, provided visibility rules permit access. The value does not belong to any single execution frame. It is part of the program’s long-lived state.

Comparing this behaviour with the previous discussion reveals something subtle but important. Both persistent_value (declared static inside the function) and global_counter exhibit persistence across function calls. Yet their visibility differs dramatically.

The variable inside the function remains confined to that function’s scope. The global variable is accessible from potentially any part of the program. Persistence, therefore, does not imply universal visibility.

Lifetime and visibility are independent properties of a variable.
Suggested visual: Memory view showing global_counter as long-lived program state accessible by multiple functions, contrasted with function-confined static variable placeholder

Recognizing this separation prevents a common misunderstanding. A variable may live for the entire duration of program execution while remaining visible only within a limited region of code.

Having examined variables defined by lifetime and visibility, we next consider declarations that introduce constraints not on existence, but on modification.

Const and the Meaning of “Read-Only”

The program also declares another variable whose behaviour differs in a less obvious way: 

const int system_limit = 100;

At first glance, this declaration appears to describe a variable that simply holds a fixed value. Because the value is never intended to change, it is tempting to imagine that such an object behaves fundamentally differently from other variables.

The keyword const, however, does not primarily describe where the value is stored. Instead, it describes how the program is permitted to interact with the value.

const is a rule about modification, not a guarantee about location.

The declaration states that the program must not alter system_limit after initialization. Any attempt to modify the value is treated as a violation of the variable’s contract. The constraint is therefore behavioural rather than spatial.

Where the value ultimately resides depends on decisions made by the toolchain and the memory model of the target system. On many microcontrollers, read-only data is placed into non-volatile memory because such placement is efficient and consistent with hardware capabilities. Yet this outcome is an implementation decision, not the direct meaning of const itself.

This distinction is subtle but important. A variable may be read-only while still occupying RAM. Conversely, values stored in Flash are not automatically protected by const. Mutability rules and storage choices are related but not identical.

Read-only behaviour and physical storage are independent concerns.

With lifetime and mutability now separated, we can unify the behaviour of all variables encountered so far using a single descriptive framework.

A Unified View of Variable Behaviour

The variables examined so far differ in ways that are easy to overlook when reading source code. Their declarations appear similar, yet their interaction with memory follows distinct rules. These differences become clearer when we describe variables not by keywords, but by behavioural properties.

Three independent questions fully characterize how a variable lives within a program:

  • How long does its storage exist?
  • Where is the variable visible?
  • Is the program allowed to modify its value?
Variable semantics emerge from lifetime, visibility, and mutability.

The variable temporary_value exists only while the function executes. Its lifetime is short and tied to the execution context. The variable persistent_value, though declared inside the function, survives across calls because its lifetime is detached from control flow.

The variable global_counter also persists for the duration of program execution, yet its visibility is far broader. Any function may access it, subject to scope rules. Persistence alone therefore does not determine who may observe or modify a value.

The declaration const int system_limit introduces yet another dimension. Its storage may persist like any other long-lived object, but the program is forbidden from altering its value. Mutability constraints operate independently of lifetime and visibility.

No single keyword explains a variable’s complete memory behaviour.

Seen through this lens, familiar categories acquire a more precise interpretation. A variable is not “global” merely because it is declared outside a function. It is global because of its visibility. A variable is not “static” merely because it persists. It is static because of how its lifetime is defined.

This unified model simplifies reasoning about embedded systems. Memory allocation, initialization behaviour, and runtime dynamics all follow naturally once these three properties are distinguished.

With this structure in mind, the apparent complexity of storage classes reduces to variations of a single idea: how memory must behave to support program semantics.

Where Do These Variables Actually Live?

A program written for a microcontroller is ultimately a request for physical storage. Every variable declaration, regardless of how abstract it appears in source code, must correspond to a region of memory whose behaviour satisfies the program’s expectations.

Earlier discussions introduced the idea that memory within a microcontroller is not uniform. Flash and RAM differ in persistence, speed, and mutability. The processor executes instructions from one region, modifies data in another, and relies on carefully constructed rules during startup to reconcile these differences.

Variables do not merely exist — they must inhabit memory regions compatible with their behaviour.

Consider first the declaration int global_counter = 10;. This variable must satisfy two distinct requirements. Its initial value must survive resets, yet its value must remain writable during execution. No single physical memory type directly satisfies both constraints.

The solution emerges through sectioning. The stored value 10 becomes part of the program image in Flash, while the variable’s runtime storage is allocated in RAM. During system initialization, startup code copies the value from non-volatile memory into the RAM location associated with global_counter.

The .data section represents values stored persistently but executed mutably.

The variable persistent_value, declared with the static keyword inside the function, follows a similar logic despite its different syntactic placement. Because its lifetime spans the entire execution of the program, allocating it on the stack would be impossible. Stack storage is transient by definition.

Instead, the variable is assigned storage within the same class of statically allocated memory used by global variables. Its visibility is restricted by scope rules, yet its lifetime demands permanent reservation. Memory allocation therefore reflects lifetime, not lexical position.

Static variables inside functions occupy long-lived data regions, not stack space.

The declaration int temporary_value = global_counter; exhibits the opposite behaviour. Its storage is meaningful only while the function executes. No persistence is required. No initialization must survive resets.

Such variables are allocated from the stack — a dynamically managed region of RAM whose purpose is to support short-lived execution state. Entering the function creates storage. Leaving the function releases it. The memory region itself remains fixed, but its usage continually evolves.

Stack allocation binds storage lifetime directly to execution flow.

The declaration const int system_limit = 100; introduces an often misunderstood dimension. The keyword const constrains modification through program logic. It does not intrinsically dictate where storage must reside.

On most microcontrollers, immutable values are placed into Flash because this placement is efficient. Flash preserves values across resets, consumes no RAM capacity, and naturally supports read-only access patterns. Yet this common outcome reflects an optimization strategy rather than the semantic meaning of const.

From the compiler’s perspective, const expresses an access rule. From the linker’s perspective, the object is simply data whose placement may be optimized. Under different constraints — for example, when rapid access or memory-mapped interaction is required — a const object may legitimately reside in RAM.

Mutability rules and storage placement arise from different layers of the system.

Seen collectively, these examples reveal a deeper pattern. Memory placement is not driven by keywords alone, but by behavioural requirements. Persistence, lifetime, writability, and access patterns together determine which region of memory can safely host a variable.

The linker formalizes these decisions by assigning sections to physical memory ranges. Startup code then enforces the initialization behaviours implied by those sections. Execution proceeds only after this memory contract has been satisfied.
