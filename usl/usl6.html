From geometry to storage

Up to now, we have deliberately stayed in a geometric world. We talked about directions, projections, residuals, and structure. We asked what the data looks like when viewed from the right angles.

But there is another way to look at the same story. One that a computation-minded person cannot avoid for long.

Everything we have done so far can be interpreted as a decision about storage. About how many numbers we choose to remember for each data point, and which numbers are worth keeping.

When we represented a point using a single direction, we replaced a \(d\)-dimensional vector with one scalar. When we added a second direction, we chose to store two scalars instead of the original \(d\).

Nothing magical happened. We simply decided that some numbers mattered more than others.

The decomposition we arrived at in the previous blog makes this explicit. A data point is no longer stored as raw coordinates. It is stored as a list of coefficients along carefully chosen directions, plus a residual that we may or may not keep.

This is compression in the most literal sense. Fewer numbers. Less storage. Controlled loss.

At the same time, something else has been quietly happening. Every step of this process can be written using matrices. The directions we discovered can be stacked. The coefficients can be collected. The residuals can be expressed as matrix operations.

In this blog, we will step away from geometry just enough to see how this entire story looks from a matrix and computation viewpoint. Not to replace intuition, but to make it usable.

We will ask two concrete questions. How does this decomposition reduce data storage. And how does the matrix formulation allow us to compute it efficiently for large datasets.

Counting what we store, with a concrete example

Let us make the idea of compression explicit by doing something very simple. Let us count numbers.

Suppose each data point originally lives in \( \mathbb{R}^d \). Storing one point in its raw form means storing \(d\) numbers. Storing \(n\) such points means storing \(n \times d\) numbers.

There is no interpretation here. This is just storage.

Now let us make this concrete. Imagine a dataset with:

\[ n = 100{,}000 \quad \text{points}, \qquad d = 1{,}000 \quad \text{dimensions} \]

Storing this dataset in its raw form requires:

\[ 100{,}000 \times 1{,}000 = 100{,}000{,}000 \quad \text{numbers} \]

That is one hundred million numbers, before we have done anything interesting with the data.

Now look at what changes once we adopt the representation we developed in the previous blogs.

Instead of storing each point directly, we choose a small number of directions and store how strongly each point aligns with those directions.

Suppose we decide to keep \(k = 20\) directions. For each data point, we now store only 20 numbers:

\[ (x_i^\top w_1),\; (x_i^\top w_2),\; \dots,\; (x_i^\top w_{20}) \]

Across the entire dataset, this requires:

\[ 100{,}000 \times 20 = 2{,}000{,}000 \quad \text{numbers} \]

Of course, we also need to store the directions themselves. Each direction lives in \( \mathbb{R}^{1000} \), so storing 20 directions costs:

\[ 20 \times 1{,}000 = 20{,}000 \quad \text{numbers} \]

Putting everything together, the total storage becomes:

\[ 2{,}000{,}000 + 20{,}000 = 2{,}020{,}000 \quad \text{numbers} \]

Compare this with the original one hundred million numbers.

We have reduced storage by nearly a factor of fifty, while still retaining a controlled approximation of every data point.

This is the key idea. The compression does not come from clever encoding tricks. It comes from deciding which numbers are worth remembering.

The value of \(k\) controls this trade-off. A larger \(k\) means more storage and better reconstruction. A smaller \(k\) means more aggressive compression and larger residuals.

Writing the entire dataset as a matrix

Up to now, we have described compression by talking about one data point at a time. That is useful for intuition, but it is not how computation actually happens. When datasets are large, we operate on all points together.

The natural way to do that is to stack the data into a matrix.

Suppose we collect all \(n\) data points into a single matrix:

\[ X = \begin{bmatrix} x_1^\top \\ x_2^\top \\ \vdots \\ x_n^\top \end{bmatrix} \in \mathbb{R}^{n \times d} \]

Each row of this matrix is one data point. Storing the dataset in raw form means storing this entire matrix.

Now recall what our learned directions look like. We chose \(k\) directions \(w_1, w_2, \dots, w_k\), each living in \( \mathbb{R}^d \).

Stack these directions as columns of another matrix:

\[ W = \begin{bmatrix} w_1 & w_2 & \dots & w_k \end{bmatrix} \in \mathbb{R}^{d \times k} \]

This matrix \(W\) is the object that defines our representation. It tells us which directions we care about.

Now look at what happens when we multiply the data matrix by this direction matrix:

\[ Z = X W \]

The result \(Z\) is a matrix in \( \mathbb{R}^{n \times k} \). Each row of \(Z\) contains the coefficients \((x_i^\top w_1, x_i^\top w_2, \dots, x_i^\top w_k)\) for the corresponding data point.

This matrix \(Z\) is the compressed representation of the dataset. It is exactly the collection of numbers we decided to store.

Reconstruction can also be written in matrix form. If we multiply the coefficient matrix back by the direction matrix, we obtain:

\[ \hat{X} = Z W^\top = X W W^\top \]

This matrix \(\hat{X}\) is the best rank-\(k\) approximation of the original data under the choices we have made.

The residuals we talked about earlier now appear naturally as:

\[ R = X - \hat{X} \]

Nothing new has been introduced here. We have simply rewritten the same ideas using matrices.

But this rewriting matters. It shows that compression, reconstruction, and residuals are all just matrix multiplications. This is what makes the method scalable and practical.

The one matrix that keeps showing up

Let us be very clear about what we are trying to do at this stage.

We want to find directions that allow us to store fewer numbers, while losing as little information as possible. Everything we have done so far has been a way of making this idea precise.

Earlier in this series, we arrived at these directions by thinking geometrically. We asked which direction captures the largest projection of the data. That question led us to an optimization problem.

When we worked through that optimization, a particular object appeared naturally:

\[ \sum_{i=1}^{n} x_i x_i^\top \]

At the time, this object was not introduced as a computational tool. It appeared simply because we were adding up projection contributions from all points.

Now let us look at the same quantity from a storage and computation viewpoint.

Recall that we stacked all data points into a matrix:

\[ X = \begin{bmatrix} x_1^\top \\ x_2^\top \\ \vdots \\ x_n^\top \end{bmatrix} \]

If we multiply this matrix by its transpose, we get:

\[ X^\top X \]

Writing this out explicitly shows that:

\[ X^\top X = \sum_{i=1}^{n} x_i x_i^\top \]

This is not a new object. It is exactly the same quantity that appeared earlier when we were reasoning about projections and residuals.

This is the key realization.

The matrix \(X^\top X\) contains all the information needed to decide which directions are most important for compression. We do not need to examine points one by one. We do not need to track residuals explicitly.

Once this matrix is built, the problem of finding good compression directions becomes a problem of analyzing this single object.

From a computational perspective, this is what makes the entire approach practical. From a conceptual perspective, it tells us that geometry, compression, and computation have been pointing to the same structure all along.

Why this makes the problem computable

Up to this point, everything we have done could still feel abstract. We talked about directions, projections, residuals, and compression. But none of this matters unless it leads to something we can actually compute.

The moment we recognize that all of this structure is captured by the matrix \(X^\top X\), the nature of the problem changes.

Instead of reasoning about every data point separately, we now have a single object that summarizes the entire dataset. This matrix does not grow with the number of data points. Its size depends only on the dimensionality of the data.

This is a crucial shift.

The original dataset may contain millions of points. But once we have formed \(X^\top X\), all questions about dominant directions, projection strength, and compression quality can be answered by analyzing this matrix alone.

From a computational perspective, this is exactly what we want. We replace a problem that depends on \(n\) large vectors with a problem that depends on a single \(d \times d\) matrix.

Even more importantly, the operations we need to perform on this matrix are well understood. We are no longer inventing new algorithms. We are using standard linear algebra tools that are stable, efficient, and heavily optimized.

This is why the entire earlier discussion about projections and residuals matters. It ensures that when we analyze \(X^\top X\), we are not performing an arbitrary computation. We are extracting directions that are optimal with respect to the compression goal we defined.

In other words, the matrix formulation does not replace intuition. It makes the intuition executable.

In the final section of this blog, we will step back and summarize how geometry, storage, and computation have converged to the same conclusion, and why this sets the stage for naming the method explicitly in the next blog.

What we gained by changing perspective

In this blog, we did not introduce a new idea. We changed the way we looked at an idea we already understood.

We started with a geometric story. Directions, projections, and residuals helped us understand how structure appears in high-dimensional data.

We then reframed the same story as a storage problem. Each choice of direction became a decision about which numbers to keep and which ones we were willing to discard.

Finally, we rewrote everything in matrix form. This was not a mathematical flourish. It was the step that turned intuition into something computable.

Seeing the same structure appear in the matrix \(X^\top X\) showed us that geometry, compression, and computation were never separate concerns. They were different views of the same problem.

Once the problem is expressed in this form, finding good representations is no longer mysterious. It becomes a matter of analyzing a single object that summarizes the entire dataset.

This perspective explains why unsupervised learning methods can scale to large datasets, and why they are able to discover structure without any labels or targets.

In the next blog, we will finally give a name to the procedure that has been quietly guiding everything so far. We will see how this matrix viewpoint leads naturally to a standard decomposition, and why its components are ordered by importance.
