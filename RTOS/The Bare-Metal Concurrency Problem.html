How RTOS Works

The Bare-Metal Concurrency Problem

Every embedded developer hits this wall eventually. Usually at the worst possible time. Here is what is actually happening when they do.

It starts with something that looks fine

When you first write firmware for a microcontroller, the structure feels almost obvious. You have a few things the device needs to do, so you put them in a loop and let them run forever.

while (1) {
    read_temperature();
    blink_led();
    check_uart();
}

This pattern has a name. People call it the superloop. And for small projects, it genuinely works. The code is readable, the behaviour is predictable, and you can hold the whole thing in your head at once. There is nothing wrong with it, until the moment there is.

The moment usually arrives when someone adds a timing requirement.

Say your temperature sensor is slow. It talks over I2C and takes a full 80ms to complete a read. That is fine on its own. But now there is a device on the other end of the UART connection that expects a response within 5ms of sending you a byte, otherwise it assumes you are dead and gives up. Suddenly the superloop has a problem it was never designed to solve.

Here is what actually plays out at runtime.

t = 0ms    read_temperature() starts
t = 10ms   UART byte arrives. Nobody is listening.
t = 80ms   read_temperature() finally finishes
t = 80ms   blink_led() runs (microseconds, basically instant)
t = 81ms   check_uart() runs at last
           The other device timed out at t = 15ms
           It has already given up and moved on

The CPU was not idle during those 80ms. It was busy, working hard, doing exactly what you told it to do. It just had no way to know that something more urgent had arrived and was waiting. It does not know what urgent means.

If you sit down and calculate the worst case, the situation is stark. The worst moment for that UART byte to arrive is right at the start of read_temperature(). The CPU then spends the full 80ms on the sensor read before it can do anything else. The response comes at around t=81ms. The deadline was 5ms. The system misses it by 76ms every single time, and there is nothing you can do about it from inside a superloop.

Drag the event and feel the problem

Move the slider left and right. The dominant cost is always read_temperature() — blink_led() and check_uart() are near-instant in reality. The worst case is the byte arriving at t=0, giving an 82ms response against a 5ms deadline. The only way to meet the deadline is if the byte happens to arrive in the tiny window right before check_uart() runs.

Every obvious fix creates a new problem

The first thing most people try is making the slow function faster. Tune the I2C timing, find a quicker sensor, get the read down to 5ms. And it works, until the next feature arrives. Then you tune that too. You are now in a game where every new line of code is a potential timing violation and the only way to discover it is to ship the firmware and wait for a failure report. With three tasks this is annoying. With twenty it is completely unmanageable, especially across a team where one person's slow new feature silently breaks everyone else's deadlines.

The second idea is to scatter check_uart() calls throughout the slow functions, polling more frequently so the latency stays down. This actually reduces the worst case, but it introduces something arguably worse: your temperature reading code now has UART logic inside it. The two concerns are tangled together. Any team member who adds a new slow function and forgets to add the polling calls has just reintroduced the original bug, silently, with no compiler warning and no obvious test to catch it.

The third instinct is the most technically interesting one. Use a hardware timer interrupt. Fire it every millisecond, handle UART inside the handler, stop relying on the loop to come around in time. This actually solves the latency problem. But now you have a new one.

The interrupt can fire at any moment. Including this moment:

buf[0] = 'H';
buf[1] = 'i';    // interrupt fires right here

// interrupt handler reads buf
// it sees 'H' and whatever junk was in buf[2]

buf[2] = '!';    // main loop resumes, too late

You have a race condition. The interrupt and the main loop are both touching the same memory, and sometimes they collide. The fix is to disable interrupts while you write to the buffer. But now every microsecond that interrupts are disabled is a microsecond where a time-critical event goes unheard. You have traded one problem for another and there is no clean exit from this loop of patches.

Three fixes, three new problems

Each fix moves the pain somewhere else. None of them address what is actually missing. The superloop has no concept of urgency, and you cannot bolt one on from the outside.

The two things that are actually missing

Here is the thing worth sitting with. All three of those fixes fail for the same underlying reason. The superloop is missing two capabilities that it has no way to grow into.

The first is priority. Right now, read_temperature() and check_uart() are equals. They run in the order you wrote them, for however long they need, and the CPU has no way to distinguish between them. A sensor read that can afford to wait and a UART response that absolutely cannot are treated identically. There is no mechanism to say "this one matters more right now."

The second is preemption. Even if the CPU somehow knew that the UART was more urgent, the superloop has no way to act on that knowledge. Once read_temperature() starts, it runs until it finishes. There is no mechanism to pause it, handle something urgent, and then come back and pick up exactly where you left off. The CPU is committed.

What preemption actually looks like

The hardware is identical on both sides. The only difference is whether the system can pause a running task, handle something urgent, and then resume. That single capability is what separates a superloop from an RTOS.

Priority and preemption. That is genuinely the whole story. Everything an RTOS does, every concept we cover across this series, is in service of making those two things work correctly and safely. The scheduler decides what runs based on priority. The context switch is the mechanism that makes preemption possible. Semaphores and mutexes exist to stop preemption from corrupting your shared data. It all traces back here.

A note on when you actually need this

Before we go further, something worth being honest about. The superloop is not a bad pattern. It is the right pattern for a huge amount of real embedded firmware running in real products right now. If your loop completes in 2ms and your tightest deadline is 50ms, you have margin you will never come close to exhausting. Adding an RTOS to that system would bring complexity, overhead, and more places for things to go wrong, in exchange for nothing.

The honest question is not "should I use an RTOS" but "do my tasks actually have conflicting timing requirements?" If the answer is no, keep the superloop. If the answer is yes, and you cannot resolve the conflict by just making things faster, then you need something that genuinely understands time. Speed is not always the answer either. If you have a control loop that must respond in 500 microseconds, no amount of function optimization will make a superloop meet that on a typical microcontroller. The problem is not the speed. It is the architecture.

The superloop fails not because it is slow but because it cannot say that some work matters more than other work. Everything else follows from that one missing idea.
