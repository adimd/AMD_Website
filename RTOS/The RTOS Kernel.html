How RTOS Works

The Kernel: What It Is and What It Is Not

The kernel is not the whole operating system. It is the part everything else depends on. Getting that distinction right changes how you think about everything in embedded development.

The head chef analogy

Think about a restaurant kitchen. There is a head chef. They do not cook every dish, source the ingredients, design the menu, or serve the tables. What they do is decide who handles what, when. They look at all the orders that have come in, decide which cook handles which dish, manage the flow of work, and make sure nothing gets stuck waiting while something else burns.

That coordination role is what a kernel does. It is not the whole operating system. It is the core that everything else is built on top of. In a GPOS like Linux the kernel is enormous because it has to coordinate thousands of hardware types, filesystems, network protocols, and user processes all at once. In an RTOS the kernel is stripped to the bone, because the coordination problem it needs to solve is much simpler and much more precisely defined.

What the kernel manages

Whether you are talking about Linux or FreeRTOS, a kernel manages three fundamental things.

The first is the CPU. Something has to decide which task runs next and for how long. That is the scheduler, and it lives inside the kernel. Every scheduling decision involves a context switch, where the kernel saves the state of the currently running task and loads the state of the next one.

The second is memory. Something has to keep track of which parts of RAM belong to which task, hand out memory when tasks ask for it, and reclaim it when they are finished. In a GPOS this is a complex virtual memory system. In FreeRTOS it is a much simpler allocator, because tasks run from a fixed memory layout with no paging and no swapping.

The third is hardware access. Tasks need to talk to peripherals such as sensors, displays, and communication buses. The kernel mediates that access so tasks do not collide. In a GPOS this is a full device driver framework. In FreeRTOS it is more minimal, though a hardware abstraction layer often sits just below the kernel to smooth over differences between microcontrollers.

What is not in the RTOS kernel

This is where most people get surprised. When they hear the word kernel they picture something like Linux, which comes bundled with a network stack, a virtual filesystem, device driver infrastructure, a security model, and a process management layer all baked in.

An RTOS kernel has none of those things. Not because they are unimportant, but because they are not the kernel's job. They are separate components that sit on top of the kernel, added when the application needs them.

Think of it like building a car. The kernel is the engine. It makes everything run. The steering wheel, GPS, air conditioning, and radio are separate systems that connect to the engine. You only include what that particular car needs. A FreeRTOS-based system that needs TCP/IP networking brings in a library like lwIP and sits it on top of the kernel. One that needs a filesystem adds FatFS. One that needs USB adds TinyUSB. The kernel itself does not change. It stays small, readable, and deterministic regardless of what gets stacked on top.

Linux vs FreeRTOS — what lives where

In Linux, almost everything is part of the kernel or tightly coupled to it. In FreeRTOS, the kernel is one small layer. Everything else — networking, filesystems, drivers — is optional and lives above it. The kernel does not know or care what is stacked on top.

The four things inside the FreeRTOS kernel

If the kernel is small, what is actually in it? Four things, and nothing else.

The scheduler

The code that decides what runs next. FreeRTOS uses a priority-based preemptive scheduler with a ready list, a data structure that tracks every task waiting to run, sorted by priority. The moment a higher-priority task becomes ready, the scheduler kicks in and performs a context switch. We will go deep on the internals of this in Phase 2, including what the ready list looks like in memory and how the context switch works in assembly.

Task management

The code for creating tasks, deleting them, suspending them, and resuming them. Each task gets its own stack, a private chunk of RAM where its local variables, function call chain, and return addresses live. The kernel tracks every task through a data structure called the Task Control Block, or TCB. The TCB is a small struct that holds everything the scheduler needs to know about a task: its priority, its current state (running, ready, blocked, or suspended), and its stack pointer so the kernel knows where to restore execution from after a context switch.

Synchronisation primitives

The tools that let tasks communicate and coordinate safely. Semaphores, mutexes, queues, and event groups. These are the building blocks for passing data between tasks and signalling that something has happened, without corrupting shared state. Phase 3 of this series is entirely dedicated to these.

The tick interrupt

A hardware timer fires at a fixed, regular rate — the system tick. Every time it fires, the kernel wakes up briefly, checks whether any sleeping tasks have waited long enough to be woken, updates the tick counter, and decides whether a context switch should happen. This is the kernel's heartbeat. If the tick fires at an inconsistent rate, the kernel's entire sense of time drifts. A task told to sleep for 100ms might sleep for 87ms or 113ms. Timeouts become unreliable. Every timing guarantee the system makes rests on the tick being steady.

Inside the FreeRTOS kernel

The entire kernel is four responsibilities. No filesystem, no network stack, no driver model, no shell. Just scheduling, task management, communication primitives, and time. That is all.

Why small is a superpower here

It is tempting to look at a 9,000-line kernel and see a limitation. It is worth flipping that around.

Every line of kernel code that runs is a line that could introduce unexpected behaviour, delay a context switch, or produce timing that is hard to predict. The kernel runs in the most privileged mode on the processor. Bugs there do not just crash one task, they can corrupt the entire system silently. And every line that runs on the critical path between a task becoming ready and it actually getting the CPU adds to the scheduling latency.

A small kernel means fewer places for bugs to hide. It means the worst-case timing is easier to understand and prove, because there are fewer paths through the code. As a system grows in complexity, the number of possible interactions between components multiplies, and bounding the worst case across all of them becomes progressively harder. FreeRTOS has been formally verified to the MISRA C coding standard and holds safety certifications for use in medical devices and aircraft. That kind of verification is only possible because the kernel stayed small enough to actually audit completely.

The kernel is not the operating system. It is the part of the operating system that you absolutely cannot do without. In FreeRTOS, those 9,000 lines are everything the scheduler needs to make guarantees. Nothing in them is decoration.
