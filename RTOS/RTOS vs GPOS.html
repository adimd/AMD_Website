How RTOS Works

RTOS vs GPOS

Two operating systems, two completely different jobs. Understanding why they are built differently is the key to understanding what an RTOS actually is.

Two systems, two problems

Think about your phone right now. It might be playing music, syncing email, running a background update, and waiting for you to tap the screen, all at the same time, on one processor. The software managing all of this is called an operating system, and its job is to share that processor fairly among everything competing for it. Linux, Windows, and macOS all do this. They are called General Purpose Operating Systems, or GPOSes.

Now think about the computer inside an ABS braking system. It has one job: check the wheel speed sensors, compute a correction, and send a command to the brake valve, all within about 10ms, every cycle, forever. Nobody needs fairness here. There are no other apps competing. What this computer needs is a guarantee that its one job always runs on time, no matter what. That is a Real-Time Operating System, or RTOS.

The same word covers two things with almost opposite design goals. Fair sharing versus guaranteed timing. And those two goals are fundamentally in conflict with each other.

What the GPOS scheduler actually does

The part of an operating system that decides what runs next is called the scheduler. On Linux, the default scheduler is called the Completely Fair Scheduler, or CFS. The name says it all. It tracks how much CPU time every program has received and tries to equalise it. If a low-priority task has been waiting a long time, the scheduler bumps it up. If a high-priority task just ran, it steps back in line.

This produces good average latency, meaning the typical wait before getting the CPU is short. But it gives you no control over worst-case latency, meaning the maximum time a program might ever wait. There is no rule that says "this task runs within X milliseconds." There is only fairness, which produces good average behaviour but zero guarantees.

And there is one more problem. Linux has a kernel, the core of the OS that manages hardware, memory, and system calls. When your program asks the kernel to do something (read a file, open a network connection, allocate memory), it enters kernel space. While the kernel is busy with that work, it may not be interruptible. A higher-priority task arrives and has to wait until the kernel finishes what it started. Usually this wait is microseconds and nobody notices. But "usually fine" is not acceptable for a brake controller. The time between a task becoming ready and actually getting the CPU, called scheduling latency, is unbounded in a GPOS.

What the RTOS scheduler does instead

An RTOS uses a completely different approach called fixed-priority preemptive scheduling. Every task is assigned a priority number when it is created. The scheduler has one rule it never breaks: the highest-priority task that is ready to run gets the CPU immediately.

The word preemptive is the key part. The moment a high-priority task becomes ready, because a sensor fired, a timer expired, or another task signalled it, the OS immediately stops whatever is currently running. It saves the state of the paused task (its registers, where it was in the code, everything), runs the high-priority task to completion, then restores the paused task exactly where it left off. That save-and-restore operation is called a context switch, and it happens in a known, bounded time, typically a few microseconds on ARM Cortex-M hardware.

The scheduling latency on a well-designed RTOS is not a statistic. It is a specification. FreeRTOS on a 168MHz STM32 achieves scheduling latency in the range of 1 to 2 microseconds. That number is guaranteed, not hoped for.

What actually happens when a high-priority task becomes ready

On the left, the GPOS keeps running low and medium tasks to stay fair, even though a high-priority task is sitting ready and waiting. On the right, the RTOS stops everything the moment a higher-priority task is ready and hands it the CPU immediately. The paused tasks resume exactly where they left off once the important work is done.

The cost of real-time guarantees

This guarantee is not free. An RTOS gives up real things to buy it.

The first thing it gives up is fairness itself. A strict priority scheduler will leave a low-priority task sitting idle even when the high-priority task is just waiting for a sensor to respond. A fair scheduler would use that idle time productively. On a system with many tasks of similar importance, an RTOS can waste CPU time that a GPOS would have put to work.

The second thing is richness. Linux comes with a filesystem, a network stack, a device driver model, package management, and decades of accumulated software libraries. An RTOS gives you a scheduler and a handful of ways for tasks to communicate with each other. Want a filesystem? Pick one and integrate it yourself. Want networking? Same answer. The kernel is minimal by design. FreeRTOS is around 10,000 lines of C, small enough to read in a weekend. That minimalism is actually a feature: fewer lines of code means fewer places something unexpected can happen, which makes it much easier to prove worst-case timing behaviour. As a system grows in size, the number of possible interactions multiplies, and bounding the worst case across all of them becomes harder and harder. A small kernel keeps that problem manageable.

The third thing it gives up is memory protection. Without virtual memory, one task can accidentally write into another task's memory and the OS cannot stop it. A bug in one part of the code can corrupt data somewhere else entirely. Safety-critical systems deal with this through rigorous code review and testing rather than relying on the OS to catch mistakes at runtime.

The trade-off at a glance

Neither is better in absolute terms. Each is the right tool for a specific job. The mistake is choosing one when you actually need the other.

The pit crew analogy

Imagine two restaurants. The first is a busy café. One kitchen, lots of customers, all ordering different things. The scheduler tries to keep everyone happy, rotates through orders fairly, keeps average wait time low. Sometimes your coffee takes longer because someone else ordered first. Nobody expects a timing guarantee. That is the GPOS model.

The second is a Formula 1 pit crew. One car, every person has exactly one job, and the moment the car stops those jobs execute in a precise sequence. The target is under 2.5 seconds, every single time, not on average. That is the RTOS model.

Same basic concept, getting work done. Completely different execution, because the cost of being late is completely different.

Where each one belongs

An RTOS is the right choice when you have hard timing requirements, when you are running on a microcontroller with kilobytes of RAM, and when the system does one well-defined job. Brake controllers, pacemakers, motor drives, industrial sensors.

A GPOS is the right choice when you have lots of varied tasks, none of them demanding timing guarantees, and you want the richness of a full software ecosystem. Laptops, servers, phones, anything where average responsiveness matters more than worst-case guarantees and where the cost of a slow response is annoyance rather than catastrophe.

There is a middle ground worth knowing about: PREEMPT_RT Linux, a modified version of Linux that applies a set of patches making the kernel fully preemptible. It closes most of the scheduling latency gaps and is used in industrial systems that need better timing than standard Linux but also need the richness of a full Linux environment. It gets you much better than stock Linux, which is good enough for many applications, just not for anything requiring a mathematical proof of worst-case timing.

A GPOS asks: how do I share one CPU fairly among many competing programs? An RTOS asks: how do I guarantee the most important thing always runs first, within a bounded time? Same surface, opposite design. Choosing the wrong one is not a configuration problem. It is an architectural one that no amount of tuning will fix.
