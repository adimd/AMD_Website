What Memory Actually Is

Before arrays, before pointers, before any of it — what are we actually working with?

A long row of numbered boxes

Forget code for a moment. Forget C, forget your microcontroller, forget everything you know about programming.

Imagine a very long street. Every house on this street looks identical. Every house has a unique number on the door. And inside every house there is room to store exactly one small piece of information. One byte.

That is memory. Not a metaphor for memory. That is what memory actually is.

Each box holds one byte. Each box has a unique address starting from zero. Your STM32F4 has 128KB of SRAM which means 131,072 of these boxes, their addresses starting at 0x20000000. Your laptop has billions of them. The scale is completely different. The concept is identical.

The CPU has one job with respect to this row of boxes. It can point at a box by its address and read what is inside. Or it can point at a box and write something new into it. Read. Write. Nothing else. Everything your program ever does is ultimately one of those two operations at some address.

Memory — a row of addressed boxes
Hover a box to inspect it
Every byte in RAM has a unique address. The CPU reads and writes by address. There is no deeper mechanism than this.

The CPU cannot use memory directly

Here is something that surprises most people. The CPU does not do arithmetic on bytes sitting in RAM. It physically cannot. It has to bring the data into itself first.

Inside the CPU there are a small number of extremely fast storage locations called registers. On your STM32 (ARM Cortex-M4) there are sixteen of them, each holding 32 bits. The CPU can only operate on what is currently sitting in a register. So even adding two numbers requires four steps.

What actually happens for int c = a + b
; Step 1 — Load a from its address in memory into register R0
; Step 2 — Load b from its address in memory into register R1
; Step 3 — Add R0 and R1, put the result in R2     (this is fast)
; Step 4 — Store R2 back to the address of c in memory

Every computation follows this rhythm. Fetch from memory into registers. Operate on registers. Store result back to memory. Steps 1 and 4 touch RAM. Step 3 does not.

Now here is the problem. The CPU does step 3 in under one nanosecond. Fetching from RAM in steps 1 and 2 takes 60 to 100 nanoseconds. To put that in human terms: if the arithmetic took one second, the memory fetch would take nearly two minutes. The processor finishes its work almost instantly and then sits completely idle waiting for the data to arrive.

The fetch-operate-store cycle
Click to step through Step 1 of 4
The CPU is fast. Memory is slow. Every program ever written is constrained by this gap.
This gap between compute speed and memory speed is the most important physical fact in all of computer science. It is the reason caches exist. It is the reason data structures exist. Everything in this series is ultimately about organizing data so the CPU spends as little time waiting for memory as possible.

If you have worked with FIR filters on an STM32, you already feel this. Keeping your coefficients in a tight contiguous array means the CPU can prefetch them all into cache before the multiply-accumulate loop begins. Scatter those coefficients across random addresses and the CPU stalls on every fetch. The math is identical. The memory access pattern is what makes it fast or slow.

How that memory gets carved up

Your program does not get one undifferentiated blob of memory. It is organized into regions, each with a specific purpose. This is where the microcontroller and OS pictures diverge, so let us look at both.

On a bare metal STM32 the memory map is fixed in hardware and printed in the datasheet. There is no operating system. What you see is what is physically there. On Linux the OS inserts a layer called virtual memory — your program sees a private address space that the OS maps to physical RAM invisibly. Two programs can use the same virtual address without interfering because the OS translates each one to a different physical location.

Despite that difference in mechanism, both worlds carve memory into the same four logical rooms. Click each region below to understand what lives there.

What a variable actually is

Now that you have the physical picture of memory, let us look at what happens when you write something as simple as this:

C
int x = 42;

An int is 4 bytes. The compiler finds 4 consecutive boxes in memory and reserves them for x. Say it picks address 1000. Those four boxes now belong to x and the value 42 gets written into them.

Here is the important part. The name x does not exist at runtime. By the time your program is executing, the compiler has already replaced every use of x with the address 1000. When your code reads x, the CPU fetches 4 bytes starting at address 1000. When it writes to x, it writes 4 bytes to address 1000. The name was only ever for your benefit while writing the code.

You can see this yourself. The & operator in C means "give me the address of this variable."

C — run this and look at the output
#include <stdio.h>

int main() {
    int x = 42;
    printf("value   : %d\n",  x);
    printf("address : %p\n",  (void*)&x);
    printf("size    : %zu\n", sizeof(x));
    return 0;
}

That address in the output is real. It is where in your RAM those 4 bytes are sitting right now. On an STM32 it would be somewhere in SRAM starting at 0x20000000. On Linux it will be on the stack. The address changes each run because the OS randomizes stack positions for security, but the size will always be 4 for an int.

Now change int to char and run it again. Size becomes 1. Change to double and it becomes 8. The type tells the compiler two things: how many bytes to reserve, and how to interpret those bytes when reading them back. The type is not stored in memory. Only the raw bytes are stored. That knowledge lives only in your source code and in the compiler.

A variable is bytes at an address
Type Value 
The name exists only in your source. At runtime there is only an address and bytes. The type decides how many bytes and how to read them.
A variable is not a named box. It is a named address. The name is yours. The address is the machine's. When the program runs, only the machine's version exists.

Why this is the foundation of everything that follows

Every data structure in this series is built on exactly what you just learned.

An array is multiple values of the same type placed at consecutive addresses. Because they are consecutive, the address of any element can be calculated with simple arithmetic. That is why array access is instant. Not because of any special property of arrays as an abstract idea. Because of consecutive addresses and arithmetic on those addresses.

A pointer is a variable whose value is an address. Instead of storing 42 it stores 1000. Instead of holding data it holds a location. Once you see every variable as bytes at an address, a pointer is not mysterious at all. It is just a variable whose bytes represent another variable's address.

A linked list is a chain of structs scattered across the heap, each one holding the address of the next. The only thing connecting them is addresses stored inside addresses. No contiguity, no arithmetic shortcut. Just pointers chasing pointers through memory.

All of it comes back to this. Memory is a flat row of bytes. Variables are names for addresses. Every data structure is a decision about how to arrange those bytes and navigate between them.
