Linked Lists — Operations

Insertion, deletion, the doubly linked list, and the honest comparison against arrays.

The operation that justifies the whole structure

In the last post you saw that a linked list is a chain of nodes scattered across the heap, connected by pointers. You saw how to walk it. Now the question is: what can you do with it that an array cannot do as efficiently?

The answer is insertion and deletion — but with an important nuance that most explanations skip. Both operations have two parts: finding the position and performing the change. The linked list only wins on the second part. Understanding exactly where the win applies is the whole point of this post.

Insertion at the front — prepend

With an array, inserting at position 0 shifts every element. Ten thousand elements means ten thousand moves regardless of what value you are inserting.

With a linked list, inserting at the front is three steps regardless of how long the list is. Create a new node. Point it at the current head. Return it as the new head.

C — prepend
Node* prepend(Node *head, int value) {
    Node *n  = malloc(sizeof(Node));
    n->value = value;
    n->next  = head;   // new node points to old head
    return n;           // caller assigns this back to head
}

// usage
head = prepend(head, 10);

The order of the two middle lines matters. You must point the new node at the old head before updating head. If you update head first, you lose the reference to the old list.

Nothing in the existing list moves. Nothing shifts. The only change is one new node and one pointer update. A million-node list takes the same three operations as an empty one. That is O(1).

Prepend — inserting at the front step by step
The existing nodes never move. Only one new node is created and one pointer is updated. The list length is irrelevant to the cost.

Insertion in the middle — insert after

Inserting after a known node requires rewiring two pointers. The new node takes the place between prev and whatever prev used to point to.

The order is critical: connect the new node forward first, then redirect prev. If you redirect prev first, you lose the reference to the rest of the list.

C — insert after a known node
void insert_after(Node *prev, int value) {
    if (prev == NULL) return;

    Node *n    = malloc(sizeof(Node));
    n->value   = value;
    n->next    = prev->next;   // step 1: connect forward first
    prev->next = n;             // step 2: then redirect prev
}

If you already have a pointer to prev, this is O(1). Two pointer assignments. No shifting. No copying. No matter how long the list is.

If you have to find prev first by walking from head, that walk is O(n). The insertion itself stays O(1) — but the total operation becomes O(n) because of the search.

Both arrays and linked lists are O(n) for insertion when you include the search. The linked list's advantage only shows when you already have the position, or when you are always inserting at the front where head gives you O(1) access.
Insert after — two pointer assignments, nothing moves
Step 1 connects the new node forward. Step 2 redirects prev. If you reverse the order, the reference to the rest of the list is lost permanently.

Deletion

Deletion is the same two-pointer logic as insertion but in reverse. Instead of inserting a new node between two existing ones, you cut an existing node out of the chain.

The core operation is a bypass. You find the node before the target — prev. You set prev->next to skip over the target and point directly at whatever came after it. Then you free the target.

C — delete the node after prev
void delete_after(Node *prev) {
    if (prev == NULL)       return;
    if (prev->next == NULL) return;

    Node *target   = prev->next;        // node to remove
    prev->next     = target->next;      // bypass it
    free(target);
    target         = NULL;
}

Again the order matters. Save target before bypassing. Bypass before freeing. If you free first, you can no longer read target->next to complete the bypass.

Deleting the head — special case

The bypass requires a prev node. The head has no prev. So deleting the head is handled separately.

C — delete head
Node* delete_head(Node *head) {
    if (head == NULL) return NULL;
    Node *new_head = head->next;
    free(head);
    return new_head;   // caller updates head
}

head = delete_head(head);

Deleting by value

C — delete node with a specific value
Node* delete_value(Node *head, int value) {
    if (head == NULL) return NULL;

    // special case: target is the head
    if (head->value == value)
        return delete_head(head);

    // walk — stop one node BEFORE the target
    Node *prev = head;
    while (prev->next != NULL && prev->next->value != value)
        prev = prev->next;

    if (prev->next != NULL)
        delete_after(prev);

    return head;
}

Notice the walk stops one node before the target — at prev, not at the target itself. You need prev to perform the bypass. This is the key difference from a search where you stop at the target.

Deletion — the bypass operation step by step
The bypass cuts the target node out of the chain. Surrounding nodes never move. One pointer change, one free.

The doubly linked list

Every operation above has one limitation. In a singly linked list you can only walk forward. If you have a pointer to a node and want to delete it, you still need to walk from head to find its predecessor — because the bypass requires updating prev->next and you have no way to reach prev from the node itself.

The doubly linked list fixes this by adding a second pointer to each node pointing backward.

C — doubly linked list node
typedef struct DNode {
    int           value;
    struct DNode *next;
    struct DNode *prev;   // points backward to the previous node
} DNode;

With both neighbors directly accessible, deletion of a known node becomes O(1). No walking needed.

C — delete a known node in a doubly linked list
void delete_node(DNode *node) {
    if (node->prev) node->prev->next = node->next;
    if (node->next) node->next->prev = node->prev;
    free(node);
}

Three lines. Both neighbors update their pointers to skip over the deleted node. No walking from head. The cost is one extra pointer per node — 8 bytes on a 64-bit system — and the payoff is O(1) deletion anywhere in the list when you have the pointer.

Doubly linked list — O(1) deletion of a known node
With prev pointers, each node can reach both its neighbors directly. No walk from head needed. Deletion is O(1) the moment you have the pointer.

The thing complexity analysis does not tell you — cache behavior

Looking at the table you might conclude that linked lists are broadly competitive with arrays and better in several cases. That conclusion is technically correct but practically misleading because of something the O notation deliberately ignores: the constant factor.

When your CPU fetches memory it does not fetch one byte. It fetches a cache line — 64 bytes on modern hardware. When you traverse an array, the next element is almost certainly already in the same cache line. The CPU prefetcher detects the sequential access pattern and loads data ahead of time automatically. Array traversal is extremely fast.

When you traverse a linked list, every node is at a random address on the heap. Each pointer follow potentially lands on a completely different cache line. No prefetching helps. Each step can cause a full cache miss costing 60 to 100 nanoseconds.

In practice this means sequential traversal of a linked list is dramatically slower than an array traversal of the same data, even though both are O(n). The O notation says the same thing. The hardware says something very different.

On your STM32 this matters even more. The L1 cache is tiny, RAM is slow relative to the CPU, and the heap is small. Scattered nodes mean scattered fetches. An array traversal can be multiple times faster than a linked list traversal even for identical algorithmic complexity.

The honest tradeoff

Use an array when you access elements by index frequently, traverse sequentially, or know the size roughly in advance. The cache behavior alone makes it the default choice for most workloads.

Use a linked list when you insert or delete at the front constantly, when you are building a stack or queue, or when you already have pointers to positions and need O(1) insertion and deletion at those positions. The browser history, the undo stack, the task scheduler in an RTOS — these are natural fits.

The linked list is not a general-purpose array replacement. It is a specialized tool for programs that insert and delete constantly at known positions and rarely need random access. In every other case the array wins — not just algorithmically but physically, because of how caches work.
