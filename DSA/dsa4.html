DSA from First Principles

Arrays

The most natural thing you can do with memory — and why a single question about resizing leads deep into the mathematics of geometric series.

The most obvious idea in computing

You need to store five integers. You know memory is a flat row of bytes. The most natural thing you can possibly do is put them next to each other. Five integers, each four bytes, placed one after another in a contiguous block.

That is an array. Not a data structure with special properties. Not something the language invented. Just multiple values of the same type placed at consecutive addresses. The idea is so direct it barely needs a name.

C
int arr[5] = {10, 20, 30, 40, 50};

In memory this looks exactly like you would expect. No gaps. No metadata stored alongside the values. No length field hidden somewhere. Just the integers, one after another.

An array in memory
Hover an element to inspect it
Five integers. Five consecutive addresses. No gaps, no metadata, no hidden machinery. This is the complete physical reality of an array.

Why random access is instant

Because the elements are contiguous and all the same size, the address of any element is a simple arithmetic calculation.

address of arr[i] = base_address + i × sizeof(element) // arr[3] with base address 1000: 1000 + 3 × 4 = 1012 → go directly there, read 4 bytes

The CPU goes directly to that address and reads. One arithmetic operation. One memory fetch. It does not matter whether you are accessing element 0 or element four million. The calculation takes exactly the same time. That is why array access is O(1). Not because someone decided arrays should be fast. Because of arithmetic on a flat memory space.

Random access — one calculation, direct address
Index
Drag to any index. The address is computed instantly — no searching, no walking. This is O(1) access.

The cost of every operation

The array's superpower is index access. Its weakness is everything that involves shifting. Understanding why each operation costs what it does comes directly from the physical layout.

Insert at the end — O(1)

If there is room, just write to the next address and increment your size counter. One operation regardless of how many elements already exist.

C
arr[size] = new_value;
size++;

Insert in the middle — O(n)

To insert at position 2 in an array of 1000 elements, every element from position 2 onwards has to shift one place to the right to make room. That is 998 writes before you can place the new value. In the worst case inserting at position 0 you shift every single element.

C
void insert(int *arr, int *size, int idx, int value) {
    for (int i = *size; i > idx; i--)
        arr[i] = arr[i - 1];   // shift right to make room
    arr[idx] = value;
    (*size)++;
}

Delete from the middle — O(n)

Same problem in reverse. Every element after the deleted position has to shift one place left to close the gap.

C
void delete(int *arr, int *size, int idx) {
    for (int i = idx; i < *size - 1; i++)
        arr[i] = arr[i + 1];   // shift left to close the gap
    (*size)--;
}
Insertion and deletion — the cost of shifting
Insert at position 2
Every element after the insertion point has to move. The further left you insert, the more work it takes.

Stack vs heap — where the array lives

A stack array is declared with a fixed size at compile time. It appears instantly, costs nothing to allocate, and disappears the moment the function returns. You cannot resize it and you cannot safely return it to a caller. On your STM32 this comes directly out of your limited SRAM stack space.

C — stack array
int arr[5];                          // uninitialized, contains garbage
int primes[5] = {2, 3, 5, 7, 11};   // initialized

A heap array is requested at runtime with malloc. It persists until you free it. It can be any size you determine while the program is running. You can return it from functions. You are entirely responsible for freeing it — and on an STM32 with a small heap, a failed malloc returning NULL is not a theoretical concern.

C — heap array
int n = 100;
int *arr = malloc(n * sizeof(int));
if (arr == NULL) return -1;   // always check
free(arr);
arr = NULL;

The fixed size problem — dynamic arrays

Both stack and heap arrays have a fixed capacity at creation. What happens when you need more space? On a stack array you write past the end into memory you do not own. On a heap array you can solve it properly: allocate a larger block, copy everything over, free the old one. This is the dynamic array.

C — dynamic array
typedef struct {
    int  *data;
    int   size;       // elements currently stored
    int   capacity;   // elements the allocation can hold
} DynArray;

void da_push(DynArray *da, int value) {
    if (da->size == da->capacity) {
        da->capacity *= 2;   // double when full
        da->data = realloc(da->data, da->capacity * sizeof(int));
    }
    da->data[da->size++] = value;
}

Why multiply by 2? Why not just add 1 each time? This question has a precise mathematical answer, and working through it reveals something fundamental about how cost accumulates. We will look at three strategies and derive the exact total copy work for each one.

The resize question — three strategies, one winner

Every time the array fills up, we allocate a new block and copy everything over. That copying is expensive. We want to minimize the total copying work across all n pushes. Let us define this precisely:

What we are measuring
T(n)= total copy operations to push n elements
T(n) = O(n)→ average per push = O(1)this is what we want
T(n) = O(n²)→ average per push = O(n)gets worse as n grows

Strategy 1 — grow by 1 each time

Every time the array is full, allocate a new block exactly 1 element larger. Starting capacity = 1.

Copy work at each push
Push 1capacity 1, first allocation0 copies
Push 2resize to 2, copy 1 element1 copy
Push 3resize to 3, copy 2 elements2 copies
Push 4resize to 4, copy 3 elements3 copies
...
Push nresize to n, copy n-1 elementsn-1 copies
T(n)= 0 + 1 + 2 + 3 + ... + (n-1)

This is the sum of the first n-1 non-negative integers. The closed form is:

Result — strategy 1
T(n)= n(n-1)/2 = O(n²)
avg per push= T(n)/n = (n-1)/2 ≈ n/2 = O(n)
n = 1,000499,500 total copies → 499 per push
n = 10,00049,995,000 copies → 4,999 per push

The more elements you push, the more expensive every individual push becomes. The problem is that every single push triggers a resize and every resize copies the entire history of previous pushes. The work from the past is being paid again and again.

Strategy 2 — grow by a fixed amount c

Instead of growing by 1, grow by some fixed constant c every time. With c = 10: capacities go 10, 20, 30, 40 ...

Resizes happen at pushes c, 2c, 3c ... The copy work at each resize is c, 2c, 3c ... After n pushes there are n/c resize events. Total copy work:

Derivation — strategy 2
T(n)= c + 2c + 3c + ... + (n/c)·c
= c × (1 + 2 + 3 + ... + n/c)factor out c
= c × m(m+1)/2 where m = n/carithmetic series formula
= c × (n/c)(n/c + 1) / 2
= c × (n²/c² + n/c) / 2expand the bracket
= (n²/c + n) / 2multiply through by c
T(n)= n²/(2c) = O(n²)
avg per push= n/(2c) = O(n)

Still O(n²). Making c larger reduces total work by a constant factor but the shape stays quadratic. The reason is the same as strategy 1 — this is still an arithmetic series. The terms grow linearly: c, 2c, 3c ... and the sum of a linearly growing series is always quadratic.

Strategy 3 — multiply by a constant r each time

Now instead of adding a fixed amount, multiply the capacity by some constant r every time. Starting capacity = 1.

The capacities after each resize are powers of r:

Capacities and number of resizes
After k resizescapacity = rᵏ
After n elementslast capacity rᵏ = n
Number of resizesk = log_r(n)vs n resizes in strategy 1

So with ratio r, exactly log_r(n) resizes happen total. Compare that to strategy 1 where n resizes happened — one per push. The number of resizes has collapsed from n to log(n). The resizes are now exponentially rare.

Now count the copy work at each resize. At each resize you copy the old capacity into the new block:

Copy work at each resize
Resize 1old capacity r⁰ = 1copy 1 element
Resize 2old capacity r¹ = rcopy r elements
Resize 3old capacity r²copy r² elements
...
Resize kold capacity r^(k-1)copy r^(k-1) elements
T(n)= r⁰ + r¹ + r² + ... + r^(k-1)geometric series

This is a geometric series with first term a = 1, ratio r, and k terms. The formula for a finite geometric series is:

Applying the geometric series formula
S= a × (rᵏ - 1) / (r - 1)finite geometric series formula
T(n)= (rᵏ - 1) / (r - 1)with a = 1
= (n - 1) / (r - 1)substitute rᵏ = n
T(n)= (n - 1) / (r - 1) = O(n)
avg per push≈ 1/(r-1) = O(1)a pure constant — no n

The average cost per push is 1/(r-1). This is a pure constant. It does not contain n anywhere. No matter how many elements you push, the average stays fixed at this value forever. That is amortized O(1).

Why any r greater than 1 works — the geometric series dominance

The reason T(n) collapsed to O(n) is a fundamental property of geometric series: the last term dominates the entire sum.

In the series r⁰ + r¹ + r² + ... + r^(k-1), the last term is r^(k-1) = n/r. The sum of all terms before it is:

Last term dominance — why the geometric series collapses
Last term= r^(k-1) = n/r
Sum of all previous≈ n / (r(r-1))
Ratio= (last term) / (sum of all before) = r - 1
r = 2last term ≈ sum of everything before it
r = 3last term ≈ 2× sum of everything before it

The last term is always a constant multiple of everything that came before. This means the total sum is always proportional to the last term, which is n/r, which is O(n). This holds for any fixed r greater than 1. The larger r is, the more dramatically the last term dominates.

Contrast this with the arithmetic series where terms grow linearly and no single term dominates. Every term contributes proportionally and the sum reflects the full breadth — quadratic.

The convergence connection

There is a deeper way to see this. Consider the average cost per push normalized by n:

The convergence connection — average cost as a series
T(n)/n= (1/n) + (2/n) + (4/n) + ... + (n/2)/nfor r = 2
= 1/2 + 1/4 + 1/8 + ... + 1/nrewrite as fractions
geometric series with ratio 1/2 → converges to 1
In generalT(n)/n converges to 1/(r-1) for any r > 1

The average cost per push is the partial sum of a convergent geometric series with ratio 1/r. Because the series converges — because r is greater than 1 so 1/r is less than 1 — the average stays bounded by a finite constant no matter how large n grows. That constant is exactly 1/(r-1).

This is the convergence connection. The amortized O(1) per push is not a trick. It is a theorem about the convergence of geometric series.

Substituting specific values of r

The formula T(n) = (n-1)/(r-1) works for any r greater than 1. Let us see what different choices give us:

T(n) = (n-1)/(r-1) — substituting specific values
r = 1.5T(n) = (n-1)/0.5 ≈ 2navg = 2 copies/push · 33% wasted
r = 2T(n) = (n-1)/1 ≈ navg = 1 copy/push · 50% wasted
r = 3T(n) = (n-1)/2 ≈ n/2avg = 0.5 copies/push · 67% wasted
r = 10T(n) = (n-1)/9 ≈ n/9avg = 0.11 copies/push · 90% wasted
All rowsO(1) average per push — constant regardless of n

Every row is O(1) average. But look at what happens to memory waste as r grows. A larger r means fewer copies per push but more empty slots sitting unused after every resize. These are two forces pulling in opposite directions and r controls the exact tradeoff between them.

The r tradeoff — copy cost vs memory waste
Ratio r
Drag to change r. As r grows, copies per push fall but memory waste rises. Both are exact formulas — 1/(r-1) for copies, (r-1)/r for waste.

Why the three strategies produce different series

Three strategies — total copy work as n grows
n =
Grow by 1 and grow by c both produce arithmetic series — O(n²) total work. Any multiplier r greater than 1 produces a geometric series — O(n) total work. The gap widens without limit.
Growing by a fixed amount produces an arithmetic series whose sum is O(n²). Multiplying by any constant greater than 1 produces a geometric series whose sum is O(n). This is not an approximation. It is a consequence of the convergence behavior of geometric series — and it is why every serious dynamic array implementation in every language uses a multiplier, not an addend.

The pattern is clear. Anything using a fixed address is O(1). Anything involving shifting is O(n).
The array is not one data structure among many. It is the primitive everything else is built from or built to fix. The stack, the queue, the heap, the hash map — all either use arrays internally or exist because arrays handle insertion and deletion poorly.

Why the next structure exists

The array's weakness is insertion and deletion in the middle. Every time you insert at position 0 you move every element. For a system that does this constantly the array is the wrong choice. You need a structure where you can insert anywhere without touching the elements around it.

That structure is the linked list. And the reason it looks the way it does — nodes scattered across the heap, connected by pointers — is entirely a response to the array's shifting problem. It trades instant access for the ability to insert and delete without moving anything else.

That tradeoff is next.
