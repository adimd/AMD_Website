Linked Lists

What happens when you stop requiring elements to be contiguous — and what that decision costs you.

The question that creates linked lists

In the last post you saw that inserting at the front of an array shifts every element. Ten thousand elements means ten thousand moves. The cost is proportional to the length of the array and there is no trick to avoid it.

But stop and ask why that shifting is unavoidable. The answer is not "because arrays work that way." The answer goes deeper.

Shifting is unavoidable because the elements are contiguous. They sit packed together at consecutive addresses with no gaps between them. When you need to make room at position 0, the only option is to physically move everything else. The contiguity that makes index access instant is the same property that makes insertion expensive. You cannot have one without the other.

So the question becomes: what if we gave up contiguity entirely? What if each element could live at any address in memory — wherever malloc happens to find space — and we found a different way to connect them?

That question leads directly to the linked list.

The node — carry your own address book

If elements are scattered across memory with no regular spacing, arithmetic cannot find them. You need a different navigation mechanism. The solution is elegant: each element carries the address of the next one alongside its own data.

An element that stores both a value and the address of the next element is called a node.

C — the node
typedef struct Node {
    int          value;   // the data
    struct Node *next;    // address of the next node
} Node;

Two fields. Nothing more. The value field holds the data you care about. The next field holds the address of the following node. If there is no following node, next is NULL.

A linked list is a chain of these nodes. Each one lives on the heap at whatever address malloc gave it. Each one points to the next. The entire list is represented by a single pointer to the first node — the head. If head is NULL, the list is empty. Everything else is reachable by following next pointers from head.

A node — two fields, one purpose
Hover a field to see what it holds
The value field holds data. The next field holds an address. That address is what makes the chain — each node knows exactly one thing: where the next node lives.

What a linked list looks like in physical memory

This is the picture you need to hold clearly in your head throughout this topic. Everything else — insertion, deletion, traversal — is just a consequence of this layout.

Take five integers. In an array they look like this: packed together, addresses 4 bytes apart, perfectly regular.

In a linked list, those same five values are scattered. Each node was allocated separately by malloc, which handed out whatever addresses happened to be free at the time. The nodes could be anywhere in the heap — far apart, out of order, with unrelated data between them.

What connects them is not proximity but the chain of next pointers. Node at address 1000 says "the next node is at 5820." Node at 5820 says "the next node is at 312." And so on until you hit NULL.

The array is one contiguous block — one calculation reaches any element. The linked list is scattered — each element is only reachable by following pointers one at a time from the head.

The arrow operator — because you always have a pointer

In a linked list you never hold a node directly. You always hold a pointer to a node — an address. This distinction changes how you access fields.

With a struct held directly, you use the dot operator:

C — struct held directly
Node n;
n.value = 42;   // n IS a Node, dot operator works

With a pointer to a struct, the dot operator fails. The pointer is not a Node — it is an address that points to a Node. To access a field you must dereference the pointer first, then use dot:

C — the explicit way
Node *p = malloc(sizeof(Node));
(*p).value = 42;   // (*p) dereferences p to get the Node, then .value accesses the field

The arrow operator is shorthand for exactly this pattern. It dereferences and accesses in one step:

C — arrow operator
p->value = 42;    // identical to (*p).value = 42
p->next  = NULL;  // identical to (*p).next  = NULL

Read p->value as: go to the address in p, then read the value field. Because linked list code always works through pointers, you will use -> everywhere. The dot operator almost never appears.

You can chain it too. cur->next->value means: go to cur, read its next field (an address), go to that address, read its value field. Two pointer hops in one expression.

Dot vs arrow — it depends on what you are holding
If you have the struct itself, use dot. If you have a pointer to the struct, use arrow. p->field is exactly (*p).field — the arrow just makes it readable.

Creating nodes and building a list

Every node is a separate malloc call. Each one lands at a different address. You connect them by storing one node's address inside the previous node's next field.

C — building a three-node list
int main() {
    // three separate heap allocations — three different addresses
    Node *a = malloc(sizeof(Node));  a->value = 10;  a->next = NULL;
    Node *b = malloc(sizeof(Node));  b->value = 20;  b->next = NULL;
    Node *c = malloc(sizeof(Node));  c->value = 30;  c->next = NULL;

    // connect them by storing addresses in next fields
    a->next = b;   // a's next field now holds the address of b
    b->next = c;   // b's next field now holds the address of c
                   // c->next stays NULL — end of list

    Node *head = a;   // the list is just a pointer to the first node
}

After those two assignments the three nodes are connected. a->next holds b's address. b->next holds c's address. c->next is NULL. The list is: 10 → 20 → 30 → NULL.

The nodes can be at address 1000, 58200, and 312 respectively — it makes no difference. The chain works because each node carries the address of the next, not because of any spatial relationship between them.

Walking the list

To visit every node you start at head and follow next pointers until you reach NULL. There is no other way. You cannot skip to the middle. You cannot calculate where node 4 lives. You must walk from the start every time.

C — traversal
Node *cur = head;
while (cur != NULL) {
    printf("%d\n", cur->value);
    cur = cur->next;   // move to the next node by following the pointer
}

Each iteration of the loop does one pointer follow. One memory fetch to a potentially random address. Five nodes means five fetches. One million nodes means one million fetches, each one potentially at a completely different location in memory.

Walking the list — one pointer follow at a time
There is no shortcut to the middle. cur must travel through every node between head and the destination. This is the cost of giving up contiguity.

Freeing a list — every node is separate

This catches people the first time. You cannot just free(head). That frees only the first node. The remaining nodes are still on the heap, now completely unreachable — a memory leak.

Every node was a separate malloc so every node needs a separate free. The pattern requires saving next before freeing, because once you free a node you can no longer read its fields:

C — freeing every node correctly
Node *cur = head;
while (cur != NULL) {
    Node *next = cur->next;   // save next BEFORE freeing
    free(cur);                // free this node
    cur = next;               // move to the saved next
}
head = NULL;               // good habit — null the head after freeing

NULL and dangling pointers — the two crashes

Linked list code chases pointers constantly. Two bugs are almost inevitable until the mental model is solid. They look similar but behave very differently.

NULL pointer dereference

NULL is zero. When you dereference a NULL pointer — p->value when p is NULL — the CPU tries to access address 0. The OS marks that address as invalid specifically to catch this. The crash is immediate, loud, and points you directly to the line that caused it. On Linux a segfault. On your STM32 a hard fault.

Dangling pointer dereference

A dangling pointer holds the address of memory that has been freed. The pointer variable still contains the old address — free does not change the pointer, it only releases ownership of the memory. The bytes at that address are still physically there. When you dereference a dangling pointer the CPU happily reads whatever bytes happen to be at that address.

Three things can happen. The freed memory might still contain the old value — your program appears to work correctly and you never know anything is wrong. The heap allocator might have overwritten those bytes for its own bookkeeping — you read garbage. Another allocation might have claimed that memory — you read something from a completely different part of your program. In none of these cases does the CPU crash immediately. The bug can propagate silently for thousands of instructions before anything visibly breaks.

A NULL pointer crash is loud and localized — a gift from the OS. A dangling pointer lets corruption spread silently. Always set a pointer to NULL immediately after freeing it. If you accidentally dereference it again, you get a clean crash at the point of the mistake instead of mysterious corruption far away.
NULL vs dangling — what actually happens at the hardware level
Same symptom on the surface — wrong memory access. Completely different consequences. One crashes immediately. The other might not crash at all.

The complete picture so far

A linked list is a chain of nodes, each one on the heap at a separate address, each one holding the address of the next. The entire list is represented by a single head pointer. Navigation is by pointer following — sequential, one node at a time, always starting from head.

You gave up contiguous memory. In return you got flexibility of layout — nodes can live anywhere, in any order, allocated and freed independently. Whether that flexibility is worth the cost of losing direct index access is the question the next post answers — with insertion, deletion, and the full comparison against arrays.
