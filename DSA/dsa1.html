DSA from First Principles

Why DSA Exists

Not what it is. Not how to learn it. Why it had to be invented at all.

Start with the machine, not the textbook

Every DSA course starts the same way. Here is an array. Here is a linked list. Here is notation for measuring cost. And within a few hours you are staring at problems about finding the kth largest element in a stream, wondering what any of this has to do with writing real software.

So let us start somewhere different. Let us start with why any of this needed to exist in the first place.

Your computer has a processor and it has memory. The processor does arithmetic. Memory holds data. The processor's entire job is to fetch data from memory, do something to it, and put it back. That is the complete picture of computation. Everything else — operating systems, compilers, databases, web browsers — is built on top of that loop.

Now here is the thing nobody tells you early enough. The processor is fast and memory is slow. Not a little slow. Dramatically slow. A modern CPU executes an arithmetic instruction in under a nanosecond. Fetching something from RAM takes 60 to 100 nanoseconds. Your processor is sitting idle, waiting for data to arrive, for most of its life.

The fundamental problem that DSA exists to solve is this: you have a finite, slow memory and a fast processor, and you need to organize data so that the operations you care about are as cheap as possible given those physical constraints.

The cost of a bad choice

Imagine you are building a contacts app. A user types a name and you need to find their phone number. You have ten thousand contacts stored in memory. The simplest thing you could write is a loop that checks every single contact one by one until it finds the right name.

C — searching through every contact
for (int i = 0; i < total_contacts; i++) {
    if (strcmp(contacts[i].name, query) == 0)
        return contacts[i].phone;
}

This works. With ten thousand contacts it is probably fine. But now think about what a real phone carrier runs. Hundreds of millions of records. Thousands of lookups per second. That same loop now does hundreds of millions of comparisons for every single search. The system collapses under its own weight.

The problem is not the code. The problem is that a flat list is the wrong way to organize this data for the operation we care about. If instead we organized the contacts into a structure that knew something about the ordering of names, we could find any contact in a handful of comparisons regardless of whether there were ten thousand records or a hundred million.

That is exactly what a well-chosen data structure gives you. Not a marginal improvement. A fundamental change in how the work grows with the size of the problem. This is the question DSA keeps asking: given what I need to do with this data, what is the right way to organize it?

You have been doing this already

If you work in embedded systems, you have been making DSA decisions your entire engineering life. You just did not have the vocabulary for them.

Your UART receive buffer is a queue. Bytes arrive in order and get processed in order, first in first out. You probably implemented it as a circular buffer, which is exactly the standard queue implementation. Your FreeRTOS scheduler uses a heap internally — every time it picks the next task to run it extracts the highest priority item from a priority queue. Your ADC sample buffer is an array, and the sliding window you run over it for filtering is a named algorithmic pattern. The FFT you use for spectral analysis exists specifically because the naive approach to the same computation grows impossibly expensive at large sizes, and someone found a smarter organization.

DSA is not foreign to embedded work. It is embedded work, formalized. The difference is that with the formal vocabulary and the underlying theory, you can reason about cost before you write a single line of code, and recognize the same patterns appearing across completely different domains.

Why this is not just for interviews

A lot of people learn DSA purely to pass technical interviews at product companies. That is a valid goal and this series will get you there. But it is worth being clear about what the interview is actually testing.

No company expects you to implement a red-black tree on the job. What the interview is testing is whether you can look at a problem, understand its structure, identify the cost of different approaches, and make a reasoned choice. That is a skill that matters every single day in real engineering work. The interview problem is just a compressed, observable version of it.

The engineer who understands why a hash map gives fast lookups will make better database schema decisions. The engineer who understands why a heap works for priority queues will write a better task scheduler. The engineer who understands the cost of copying versus the cost of pointer chasing will write better firmware for memory-constrained hardware.

DSA is the study of how to organize and operate on data given the physical realities of hardware. Understanding it does not make you better at interviews. It makes you a better engineer, and that is what makes you better at interviews.

What this series is

We are going to build every major data structure from scratch in C. Not call a library. Not use a container. Build it from raw memory, because the only way to truly understand what is happening is to write the code that makes it happen, look at the memory layout, and trace through every operation by hand.

The order matters. We start with memory itself because everything in DSA is ultimately a decision about how bytes are arranged in RAM and how the processor moves through them. From that physical foundation, arrays emerge naturally. From arrays, the limitations that make linked lists necessary become obvious. From the experience of using both, the need for a language to compare their costs becomes clear. Every topic arrives because the previous one made you feel the need for it.

By the end you will not just know what a binary search tree is. You will know why it exists, when it is the right tool, what happens to it when you use it wrong, and how to explain that reasoning to anyone in the room. That is the goal. Not memorization. Understanding.
