Probability as a Computational Object

The Function Behind the Randomness

A random variable is not a varying number. It is a deterministic function with a randomly-sourced input. Once you see that, everything else clicks.

A warning about the name

I have to tell you the bad news up front. The thing we are about to learn is called a "random variable," and the name is one of the worst pieces of terminology in mathematics. It sounds like it should be a variable that is somehow random. That is wrong. A random variable is not a variable. It is not random. It is a function. A perfectly ordinary, deterministic function. The "random" part refers to where its input comes from, not to anything about the function itself.

If you can hold that idea in your head from the start, you will skip the weeks of confusion most beginners spend trying to figure out what those two words could possibly mean together. The two words together mean a function. That is the whole secret. The rest of the class is just making peace with this fact.

Where we left off

End of Class 2. You roll two dice. The sample space is 36 ordered pairs:

Ω = { (1,1), (1,2), (1,3), ..., (6,5), (6,6) }

The dice physically produce pairs. That is the random experiment. Each pair is one outcome.

But you almost never care about the pair. You care about the sum. Or the maximum face. Or whether the two dice came up the same. None of those quantities is in the sample space. The sample space contains only pairs. The sum, the max, the "are they equal" indicator, all live somewhere else.

Where do they live? That is the question this class answers.

The first random variable

Let me just define the thing.

A random variable is a function from outcomes to numbers.

That is the whole definition. It takes the atomic outcome of the experiment as input, and produces a number as output. For the two-dice experiment, "the sum" is a random variable. It is a function. In code:

int sum_of_dice(pair_t outcome) {
    return outcome.d1 + outcome.d2;
}

You give it the outcome (3, 4). It returns 7. You give it (6, 6). It returns 12. You give it (1, 1). It returns 2. That is a random variable. A function whose input is an outcome from the sample space and whose output is a number.

Here is another, so you see this is not a one-off. "The maximum face value":

int max_of_dice(pair_t outcome) {
    return max(outcome.d1, outcome.d2);
}

Same input type. Same output type. Different mapping. Different random variable. And a third one. "Are the two dice equal":

int dice_are_equal(pair_t outcome) {
    return (outcome.d1 == outcome.d2) ? 1 : 0;
}

This one returns 0 or 1 instead of 2 through 12, but it is still a function from outcomes to numbers. Still a random variable.

Switch between the three random variables and watch what happens. Same sample space, three different functions, three different output structures. The sum maps 36 pairs into 11 possible values. The max maps them into 6. The equality indicator maps them into 2. The function is deterministic in every case. What changes between runs of the underlying experiment is which pair gets fed in, not what the function does with it.

That is the move. The sample space had 36 elements, each one a pair of integers. Pairs are not numbers. You cannot add pairs. You cannot take the average of pairs. You cannot say "the pair was greater than 7." The sample space is full of atoms that are not numerical, even when the experiment seems numerical.

The random variable is the bridge. It takes whatever the experiment physically produces and projects it onto the number line, where you can do everything you know how to do with numbers.

This is why the random variable exists as a separate object from the sample space. The sample space describes what the world produces. The random variable describes what you compute from what the world produces. They are different things, and the random variable is the bridge between the experimental reality and the mathematics you want to apply to it.

The notation, and why it looks weird

There is a notation convention I have to warn you about, because it confuses everyone the first time.

In maths, random variables are usually given capital letters. X, Y, Z. The specific value a random variable takes on a particular run is given a lowercase letter, usually the matching one. So you might read:

Let X be the sum of two dice. Then P(X = 7) = 6/36.

In code terms, what this is saying is:

  • X is the function sum_of_dice. The random variable.
  • X = 7 is the event that this function returned 7 on this run. The event consists of all outcomes (pairs) that the function maps to 7.
  • P(X = 7) is the probability of that event.

Notice the slippage. "X" is a function. "X = 7" is an event (a set of outcomes). The textbooks use the same letter for the function and for the value it returned, and you are supposed to figure out which one from context. This is bad notation but it is the notation everyone uses, so we have to live with it.

When you read X = 7, mentally translate to "the random variable X took the value 7 on this run," which is the same as "this run's outcome was one of the pairs that the function maps to 7."

If you do not have this translation in your head, the math notation in every probability book will feel like it is hiding something. Once you do, it becomes routine.

The random variable creates events

Here is the move that makes random variables useful, and it is the move that connects this class to last class.

Take the random variable X = sum_of_dice. The statement X = 7 defines an event on the sample space. Which event? The set of all outcomes that the function maps to 7. From last class, we know that is:

{ (1,6), (2,5), (3,4), (4,3), (5,2), (6,1) }

Six outcomes. The event "the sum equals 7" is this set of six pairs. The random variable created this event by giving us a criterion (return value equals 7) for grouping outcomes together.

This works for any value, and for any kind of question.

  • X = 2 is the event {(1,1)}. One outcome.
  • X = 12 is the event {(6,6)}. One outcome.
  • X > 9 is the event of all pairs whose sum exceeds 9. Six outcomes.
  • X is even is the event of all pairs whose sum is even. Eighteen outcomes.

Every statement you can make using the random variable's return value defines an event on the underlying sample space. The random variable is, in this sense, an event-generating machine. You hand it a condition on its output, and it hands you back a subset of the sample space.

This is going to be the engine of every probability calculation in the rest of the course. We do not compute probabilities of abstract things. We compute probabilities of events. The random variable is how we describe the events we care about, in numerical language we are comfortable with.

You have been writing random variables your whole career

Open any embedded codebase. Find any function that reads a sensor and produces a number. That function is a random variable.

The deterministic part is the function itself. Given the same input, it produces the same output. That part is not random. What is random is the input. The samples coming off the ADC are random. The features extracted from a vibration window are random. The classifier output is random because its input is random. The function is deterministic, but the function evaluated on a random input is itself a random object.

A random variable is not random because the function is random. It is random because the function takes a random input.

Once you see this, every numerical quantity in your firmware that depends on a sensor is a random variable. The voltage you read. The temperature you compute. The frequency you extract. The class label you produce. All random variables. Different ones, defined by different functions, but all of the same structural type: outcome in, number out.

The visual below shows three real firmware lines, the kind you have probably written. For each, we identify the underlying experiment, the function being applied, and the output range. This is the recognition skill the class is building. Once you can do this in your sleep, every piece of sensor-driven code in your codebase becomes legible as a random variable.

The function itself is plain ordinary code. Nothing magical about the random variable. The only thing "random" about it is what you happen to be feeding it.

A wrinkle: categorical random variables

I have been a bit loose. Let me clean up.

In the strictest mathematical definition, a random variable's output has to be a number. That is what allows you to do arithmetic with it. But in practice, especially in ML, you often want to talk about "random variables" that take values like "healthy" or "failing" or "cat" or "dog." These are not numbers.

The standard fix is: assign a number to each category. "Healthy" becomes 0, "degrading" becomes 1, "failing" becomes 2. Now the classifier is technically a function from vibration windows to the set {0, 1, 2}, which is a numerical range, and it is a proper random variable.

This is the same idea as label encoding in ML. The underlying object is categorical, and we numerically encode it so the maths machinery applies. For the rest of the course I will use "random variable" in the broader practical sense: a function from outcomes to either numbers or categories that have a numerical encoding. The strict mathematical definition is just numbers. The engineering definition includes categories.

Discrete and continuous random variables

One more distinction worth flagging early, because it is going to come up again and again.

The output of a random variable can be either discrete (a countable set of values, like {0, 1, 2} or {1, 2, ..., 6} or three motor states) or continuous (an uncountable range, like all real numbers in some interval).

  • sum_of_dice outputs an integer between 2 and 12. Discrete. Eleven possible values.
  • classify_motor_state outputs a label encoded as 0, 1, or 2. Discrete.
  • read_temperature_celsius outputs a float. Continuous (in principle; quantised in practice).
  • compute_rms outputs a float. Continuous in principle.

The maths is different in each case. For discrete random variables, you ask "what is the probability that X = 7?" and the answer is a single number. For continuous random variables, you ask "what is the probability that X is between 22.4 and 22.6?" and the answer involves an integral. Classes 4 through 6 build both versions cleanly. The vocabulary needs to be in your head now.

What you should leave with

Three things.

First, a random variable is a function. From outcomes (atoms of the sample space) to numbers (or numerical encodings of categories). It is not a varying number. It is not a random number. It is a deterministic function whose input happens to be random, and whose output inherits the randomness of the input.

Second, the random variable is the bridge between the experimental sample space (which can hold arbitrary atomic objects like dice pairs, vibration windows, raw sensor readings) and the number line (where you can do arithmetic, compare against thresholds, take averages, plot histograms). Without it, you cannot do any of those things on the raw sample space.

Third, the random variable defines events. Every statement of the form X = value or X > threshold or X is even defines a subset of the sample space: the set of outcomes for which the random variable returns a value satisfying the condition. This is how we specify the events we care about in practice. We do not point at outcomes directly. We describe them by what our random variable computes from them.

Next class, we put weights on those events. That is what a probability distribution is: a rule that assigns numbers (between 0 and 1) to events in a consistent way. The random variable describes which events exist; the distribution describes how likely they are.

Check yourself

Five questions. Pick the option you think is right. If you got it, that option turns green. If you missed, the wrong option turns red and the right one lights up too. An explanation appears underneath either way.

Question 1
In your own words, what is a random variable?
Why Right. The function is deterministic. The same outcome always produces the same number. What varies is which outcome the experiment hands you on a given run, and that variation flows through the function to produce different outputs. The terminology is misleading but the structure is simple: deterministic function, random input.
Why The name is the trap. A random variable is not a variable in the programming sense, and the function itself is not random. It is a deterministic function that maps each outcome of a random experiment to a number. The randomness lives in the input, not in the function. If the function were genuinely random (same input giving different outputs on different calls), it would not be a function at all in the mathematical sense.
Question 2
You build a smart doorbell. When someone walks up, the camera captures their face and a vision model outputs one of: family, friend, delivery, stranger. Which of these is the random experiment?
Why Exactly. The randomness is in the world (who walks up), not in the model. The vision model is deterministic: feed it the same image twice and it produces the same label twice. The model sits on top of the random experiment as a random variable, mapping outcomes (the person who arrived) to labels. Whether the model is correct or not is a separate question, not what makes this a random experiment.
Why The vision model itself is deterministic. Feed it the same image twice, same label twice. So the model is not the random experiment. What is actually random is which person walks up to the door. That is the underlying experiment. The model is the random variable: a deterministic function applied to the random input "the person who arrived."
Question 3
For a firmware function float rms = compute_rms(adc_samples, 512), what is the output range of the random variable compute_rms?
Why Right. The output range is a property of the function. It is whatever set of values the function could produce across all valid inputs, set before any particular run. The realised value on a specific run depends on the samples. The range does not. This distinction matters because next class we put probability mass on the range, and the mass has to live inside the range, not be defined per-run.
Why Two different questions are being mixed up. The realised value on this run depends on the samples (different buffers give different RMS values). The output range of the function does not depend on the samples. The range is what the function could produce across all valid inputs: bounded below by 0 because RMS is non-negative by construction, bounded above by the ADC's dynamic range. Range is a property of the function. Value is a property of one specific run.
Question 4
You roll one fair six-sided die. Let Z = the face value squared. Which event does the statement Z = 10 define?
Why Exactly. The output range of Z is {1, 4, 9, 16, 25, 36}. 10 is not in there. So the event Z = 10 is the set of outcomes for which Z returns 10, which is no outcomes at all. That is the empty set. The event is well-defined, it just contains nothing. When we put probabilities on events next class, the empty event has probability zero by definition.
Why The statement Z = 10 is still a perfectly valid event-defining condition. It is asking "for which outcomes does Z return 10?" The answer happens to be "no outcomes at all," because the squared face values are {1, 4, 9, 16, 25, 36} and 10 is not in there. That gives the empty set, which is a valid event. It is not undefined. It is well-defined and has zero outcomes. This matters because next class, "probability of the empty event" will be exactly zero, by definition.
Question 5
A colleague says "neural networks are random functions, because their weights are randomly initialised." Is this a good description?
Why Exactly the right shape of answer. Once the weights are fixed, the network is a deterministic function: same input, same output. The randomness happened before evaluation, when the weights were sampled from a distribution. This is the same trick as PRNGs: push the randomness into the parameters or the seed, keep the function itself deterministic. "Random function" in casual usage means "deterministic function whose parameters were randomly chosen." The function-evaluation step is always deterministic, because that is what "function" means mathematically.
Why The honest answer needs to separate two things. A network with specific weights is a deterministic function: same input, same output. But the weights themselves were sampled from a distribution at initialisation, so across the population of possible initialisations, you are picking a random function from a family of deterministic functions. The randomness lives in the weight selection step, not in the function evaluation step. This is the same pattern as PRNGs: deterministic function, random parameters or seed. A genuinely random function (same input giving different outputs on different calls) would not be a function at all in the mathematical sense.
